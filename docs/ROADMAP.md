# Spoor — Project Plan

> **Give your agents a map of the web.**
> Spoor is a local-first crawler that escalates from selectors to browser and visual interaction only when needed — then exposes the discovered behavior through MCP or API.
>
> **Local-first. MCP-ready. LLM optional.**

*A local-first web scraping stack that escalates through four UI tiers — fast selectors, JS-rendered selectors, visual/fingerprint healing, and human-like interaction — while passively building a map of the target's underlying API surface and a broader catalog of client-side signals (storage, console, performance, real-time traffic, and more), using existing open-source components wherever possible and LLM calls only as an optional, off-by-default last resort. A second mode (§2e, v2) turns the same machinery outward: autonomously explore every interaction a product supports and generate a browsable wiki of what happens, on every signal level, for each one — served live to agents via §2f, not just written to static files.*

**Scope note:** Windows native apps, mobile emulators, and remote mobile device farms were considered and explicitly deferred (see the cost/complexity breakdown from planning discussion — each needs a genuinely different automation stack, roughly 2–4 extra weeks apiece, and remote device farms specifically require a whole separate Appium backend since they don't expose raw ADB). Current scope is **web UI + the API surface reachable from a browser session**, nothing else.

**On the words "map" (hero sentence) and "full picture" (§2b): both mean *as complete as what Spoor has actually observed or been asked to explore*, never a guaranteed-exhaustive census of the target.** GraphQL introspection can be disabled, official spec discovery can fail to find anything, and passive traffic capture only ever sees endpoints a run actually happened to exercise. This is a documentation commitment, not just an internal caveat — user-facing copy should say "a map of what's been explored," never imply completeness it can't back up. See §2b and §2e for exactly where the boundedness comes from.

## 0. Design principle: general-purpose, never site-tailored

Everything in this plan — the four tiers, API surface discovery, the signals catalog — has to work on a target the tool has never seen before, using only what it can observe or learn at runtime. Nothing in the core is allowed to hardcode knowledge of a specific website: no `if domain == "..."` branches, no selectors or endpoint paths written against one named site, no logic that only makes sense for one target.

Two things that look like exceptions but aren't:
- **The per-domain cache** (§2, "which tier worked last for this domain") is fine — it's runtime-*learned* behavior, discovered generically the same way for every target, not hardcoded knowledge of any one site.
- **Platform-convention recognizers** (e.g. "this looks like a Shopify store, so try `/products.json`") are fine *as a pluggable, opt-in table of known platform conventions* — they generalize across every store built on that platform, not one company's site. They should live as a separate, swappable "recognizers" list the core dispatcher consults, never as logic baked into the escalation path itself.

Test fixtures (§5) are the opposite of integrations: OWASP Juice Shop, Sauce Demo, a self-hosted ERPNext/Odoo, and a self-hosted Netflix-clone exist purely to prove the generic tiers hold up across different architectural shapes (security-flavored webshop, clean webshop, auth-gated internal business app, heavy media SPA). If a fixture only passes with a special-case added for it, that's a signal the general mechanism (a tier's threshold, a selector strategy, a validation schema) isn't general enough yet — not a reason to add an exception for that fixture.

## 1. Why this project, given the landscape

Crawl4AI, browser-use, and Skyvern already do a lot of "smart scraping," but all three are built LLM-first: the model is in the loop for most decisions, which means API cost, latency, non-determinism, and a hard dependency on a cloud provider (or a beefy local model) for basic runs.

The gap this project fills is a **local-first, deterministic-by-default** stack: it runs entirely on the user's machine with no API key required, uses classical techniques (DOM fingerprinting, perceptual-hash/template matching, scored similarity) for resilience instead of a model call, and only *optionally* lets someone wire in an LLM or local vision-language model (e.g. via Ollama) for the small residue of cases nothing else can resolve. That's a genuine, defensible niche rather than a re-run of what's already popular — worth stating explicitly in the README so it's clear this isn't "another Crawl4AI."

**Who this is actually for.** Two audiences, deliberately, not one at the expense of the other: Hidden Trail's own internal use (feeding a mapped product's behavior into HT's LLM/agent workflows via §2f, and generating test automation runs from a captured map — see §2g), and an open-source release for anyone else who wants to scrape a system or turn it into a wiki. The two aren't in tension as long as §0's no-tailoring rule holds — HT's own usage is just the first, most demanding user of the same generic tool everyone else gets, not a special internal fork.

**Not an "agent."** Deliberately avoiding that framing: Spoor doesn't decide on its own what's interesting enough to look at more closely, or make autonomous judgment calls about a target. It records exactly as much as it's told to — via config (§2a), via the signal-tier flags (§2c/§2d), via an explicit exploration request (§2e). Anywhere this plan previously described a "heuristic decides" or "flags as interesting" behavior, read that as "matches an explicit, user-set rule," not the system exercising independent judgment — see the correction in §2e.

**Reliability is the one thing this cannot compromise on.** The whole product lives or dies on not being flaky. A scraper that sometimes finds the button and sometimes doesn't is worse than useless — it's actively misleading, whether a human is reading the output or an agent is acting on it via §2f/§2g. This makes tier 3 (§2, self-healing) the highest-priority piece of engineering in the entire plan, not just "the hardest part" — see §5's expanded test bench, built specifically to hold this to an honest, measured standard rather than a marketing claim.

## 2. Architecture: resolving a target vs. executing an interaction

Two separable concerns were previously described as one four-step ladder, which blurs a real distinction worth splitting out explicitly:

- **Resolution (tiers 1–3, escalating): finding the right element or piece of data on the page.** One Playwright session per job carries a request through up to three resolution tiers. Each tier validates its result against a schema before deciding whether to escalate; a small local cache remembers which tier last worked for a given domain/page-template so routine runs skip straight to it.
- **Interaction execution (a separate axis, not a fourth resolution tier): once a target is resolved, how the click/scroll/drag/type actually gets carried out.** This is a two-way choice — native/instant (Playwright's default primitives) or human-like/jittered (the Bezier-curve wrapper) — picked per-run or per-target, not escalated through in sequence the way resolution is.
- **Tier 3.5 (optional AI fallback)** extends the *resolution* ladder only — it helps find the right element when tier 3 can't, and never decides how to act on it.

| Tier | Purpose | What to depend on (not build) | LLM involved? |
|---|---|---|---|
| 1 (resolution) | Fast selectors, no browser | `httpx` + `parsel` (or Crawlee's `HttpCrawler`) | No |
| 2 (resolution) | JS-rendered pages, same selectors | Crawlee for Python's `AdaptivePlaywrightCrawler` — already auto-detects when JS rendering is needed and learns per URL pattern | No |
| 3 (resolution) | Selector broke / needs resilience | **Written from scratch** — no Healenium dependency, no vendored code; **Healenium's** published Apache-2.0 core approach (*not* the commercial "Pro" tier) is a conceptual reference only. DOM fingerprint + attribute similarity + perceptual-hash on a cropped screenshot, no model call | No (by design) |
| 3.5 (resolution, optional) | Last resort when tier 3 truly can't resolve an element | Pluggable interface — user can wire in Claude/GPT vision **or** a local VLM via Ollama (e.g. Moondream) | Optional, disabled by default |
| Interaction execution | Carrying out the resolved action: click, scroll, drag, hover, type | Playwright's native mouse/keyboard primitives; optionally wrapped with a small Bezier-curve jitter layer (the published `ghost-cursor` algorithm is easy to port; no need for the original Node library) for human-like mode | No |

The only substantial code this project actually writes is the **escalation dispatcher** (tries resolution tiers in order, validates, caches the winner per domain), the **per-tier adapters** gluing the above libraries into one consistent interface, and the **interaction executor** — a separate, much smaller piece of code that just carries out an already-resolved action, natively or jittered. Keeping these as two clearly distinct pieces (rather than one four-step list) is also what makes §2e's exploration mode make sense: it barely touches the resolution machinery at all (it discovers actionable elements directly via the accessibility tree, not via selectors), but uses the interaction executor for every single step. That keeps the "reinvent everything" surface small even with all resolution tiers in v1.

**Tier 3's uncertain-match handling (reliability-first, per §1).** When tier 3's confidence score falls below a defined "safe to auto-resolve" threshold but above zero — it found *a* plausible candidate, just not a confident one — the default is to flag it for manual review rather than silently guessing, surfaced in the run summary (§2d) as an "uncertain match" the user can approve, reject, or correct. Every tier-3 resolution, confident or not, logs its winning candidate's confidence score plus the runner-up candidates it considered — so "why did it heal to this element" is always answerable from that log, as a direct corollary of scored matching rather than a separately bolted-on feature.

**Decision — Phase-1 escalation-dispatcher seam.** The escalation dispatcher (the "only substantial code this project actually writes", above) is introduced *structurally* in Phase 1, ahead of tier 2's browser machinery, so that tier 2 slots into an existing seam rather than forcing a rewrite. `spoor/core/extract.py` selects among an ordered chain of resolvers — tier 1 (`httpx` + `parsel`, implemented) and tier 2 (JS rendering, a declared-but-stubbed rung) — via a small `Resolver` protocol; `run`/`run_report` delegate to the selected tier. Tier selection is **capability-driven** for this slice: a config requesting a browser-only capability — `pagination.infinite_scroll: true` — is one tier 1 declares it cannot resolve, so the dispatcher advances to tier 2, whose stub raises a clear "not yet available" error rather than silently mishandling it. The *other* escalation trigger described above — run tier 1, escalate when its selectors fail to validate against the schema — is deliberately deferred until tier 2 is real, because a static-vs-rendered comparison is what makes "tier 1 came up empty, try rendering" a meaningful, non-heuristic signal; inventing a content heuristic now would collide with the legitimate "missing field → null" cases (§2a). No browser dependency is added in this slice; when tier 2's real implementation lands, only the stubbed rung changes.

**Decision — Phase-1 content-driven escalation (zero-records trigger).** With tier 2 real, the escalation trigger deferred above (run tier 1, escalate when its result is empty) now lands, and the collision the earlier note flagged is resolved by choosing the trigger deliberately: the dispatcher escalates **only when tier 1 extracts zero records**, never on the strength of a null *field*. `run_report` walks the accepting tiers in order, runs the first, and advances to the next only while the result is empty — a run that yields records is returned as-is even if some of those records have null fields, because a missing optional field is a legitimate result (§2a), not a signal to re-render. This side-steps the "empty vs. legitimately-null" ambiguity structurally: in single-record mode (no `item`) tier 1 always yields exactly one record, so a null-field page never triggers escalation; only an `item` selector that matches nothing — the hallmark of a listing that populates client-side — escalates. A **robots-blocked** run is never escalated either: `blocked` is a non-empty result the block is recorded in, and re-running behind a browser would neither be permitted nor work around the disallow — the heavier tier is for rendering, never for evading politeness (§6). The trigger stays fully generic (§0): it inspects only record count, never site identity or content shape. A genuinely empty listing (e.g. a no-results search page) will escalate once and still come back empty — a bounded, correct-result cost, not a misresolution. **Render-readiness:** for this escalation to be worth anything, the browser tier must not capture the DOM *before* the SPA has populated it — `networkidle` reports the network settled, not that the listing rendered, and against the Juice Shop archetype it fires with zero `mat-card`s in the DOM. So when a config names a repeating `item`, tier 2 waits for at least one such element to attach before extracting (`page.wait_for_selector(config.item, state="attached")`, bounded by a timeout that falls through to a zero-record extraction for a legitimately empty listing). This keys entirely off the config's own selector — no site knowledge (§0) — and is what makes the empty-tier-1 → render → non-empty result deterministic rather than a race.

**Decision — Phase-1 tier-2 slice (thin Playwright adapter).** Tier 2 is built as a thin adapter over Playwright rather than by adopting Crawlee's `AdaptivePlaywrightCrawler` wholesale: it renders a page in a headless browser (`playwright.sync_api`, Chromium) and then reuses the *same* `parsel` extraction tier 1 uses on the rendered HTML, so field/`item` semantics, `attr`, and coercion are identical across tiers. This keeps our escalation dispatcher in control of tier choice (rather than delegating that to Crawlee) and keeps the dependency surface small; Crawlee remains an option if a later phase needs its request-queue/autoscaling machinery. Tier 2 honors the same `PolitenessPolicy` gate as tier 1 (robots.txt + crawl-delay, §6). Its capability this slice is **infinite-scroll pagination**: the browser scrolls to the bottom until the page stops growing (`document.body.scrollHeight` stability, a generic signal — no per-site selector knowledge), then extracts. `playwright` is added as a runtime dependency; the browser binary is installed separately (`playwright install chromium`), and CI gains that step. Tests serve the static fixtures to the real browser over a loopback `http.server` on an ephemeral port (a browser cannot use the `httpx.MockTransport` tier-1 tests rely on).

**Decision — Phase-3 tier-3 first slice (the scoring core + §5.3 corpus, no wiring yet).** Phase 3 is explicitly not compressed (§1), so tier 3 lands slice by slice; this first slice is the **pure scored-matching engine** (`spoor/core/healing.py`) plus the §5.3 mutation corpus that guards it, deliberately *without* any live-run wiring. The engine is **written from scratch** — Spoor takes no dependency on Healenium and vendors none of its code; Healenium's published Apache-2.0 core approach (not "Pro", per the tier table) served only as a conceptual reference for the shape of the idea (a DOM fingerprint + weighted similarity). What ships is entirely our own implementation: an `ElementFingerprint` captured while a selector works, and a `score` blending tag, id, class, other-attribute, inner-text, and structural (ancestor-chain + sibling-position) similarity into `[0,1]` with **no model call**. The blend is deliberately weighted toward the signals that *survive* markup churn and carry identity — inner text, a stable id, tag, structure — while class and other attributes (exactly the volatile signals a redesign churns, the ones tier 3 exists to survive) contribute but never dominate: weighting them heavily would collapse confidence in the precise case healing is for (a class rename). Signals are scored as a weighted mean over only the components the *stored* element actually had, so an element with (say) no id is never penalised for candidates that have one. `heal` picks the highest-scoring candidate; ties break deterministically toward the earlier candidate. The uncertain-match handling above is realised exactly: a best candidate `>= threshold` (default `0.6`, tunable per call) is a confident heal, one below but `> 0` is returned flagged `confident=False` for review, and an empty candidate pool yields `None`. Every result carries its winning score plus the runner-ups considered, so "why did it heal here" is answerable straight from the `HealResult` (its `explain()`), not a bolted-on log. **§5.3 corpus (merge-blocking ≥95%):** `tests/test_healing_mutation.py`, run under `pytest -m mutation`, uses `hypothesis` to generate mutation plans (class renames, attribute shuffles, sibling reordering, added wrappers, text changes from light to full reword, in combination at increasing severity), applies them *site-wide* to a known-good listing fixture, and asserts tier 3 re-resolves the correct element — tracked by lxml element *identity*, so nothing can cheat via a marker — at a rate `>= 0.95`. The corpus currently sits at **~99.8%** (min ~99.3% across independent 300-plan batches); the residual failures are the honest total-anchor-loss case (a full text reword coinciding with class/attr/id loss on an otherwise identically-structured element), which is also the uncertain-match path exercised in `features/self_healing.feature`. **Deferred to follow-on Phase-3 slices** (noted, not built here): cross-run fingerprint persistence (a per-domain cache — none exists yet in `spoor/security/storage.py`, which is per-run only), wiring tier 3 into the escalation dispatcher and surfacing uncertain matches in the run summary (§2d), and the **perceptual-hash-on-cropped-screenshot** component from the tier table (needs the browser tier, so it rides with dispatcher wiring). Nothing in this slice is site-specific (§0): the same similarity math runs for every target.

**Decision — Phase-3 tier-3 wiring slice (dispatcher + persistence + run summary).** The second Phase-3 slice makes the scoring core reachable in a live run and lands two of the follow-ons the first slice deferred: **cross-run fingerprint persistence** and **surfacing uncertain matches in the run summary (§2d)**. Three small pieces glue it together, all generic (§0). (1) `spoor/core/fingerprint_cache.py` — the per-domain persistent cache §0 explicitly sanctions as runtime-*learned* (never a site fact in source): a JSON file per target netloc under a new `fingerprints/` subdirectory of the git-ignored cache root, keyed by field name, holding the `ElementFingerprint` each field last resolved to. It is **local-only (§2h)** — a fingerprint embeds page text — and, unlike the per-run capture dirs, *persistent across runs* (that is the point). It never raises on I/O: a missing or corrupt file is a first run for the domain, not an error, and a save only writes when something actually changed. (2) `spoor/core/self_healing.py` — a run-scoped `Healer` over that cache: `remember(field, element)` fingerprints a field's element on a successful resolve; `attempt(field, root)` heals a field whose selector matched nothing, returning the element **only when the best candidate clears the confidence threshold** and recording a `HealEvent` (field name + winning confidence, **never the matched text** per §2h; `used` distinguishes a confident fill from an uncertain match). A sub-threshold best candidate leaves the field null and is flagged for review — never silently guessed (§2, §1). (3) The dispatcher (`run_report`) creates one `Healer` over the target's cache, threads it through whichever tier resolves the run (tier 1 and tier 2 both forward it to the shared `parsel` extraction), persists newly-learned fingerprints after the walk, and stamps the heal events on the `RunResult`; `RunSummary` projects them to `heal_confident` / `heal_uncertain` counts and renders a `self-healing:` line only when something healed. **Scope of this slice:** healing is threaded through **single-record configs only** (no `item`) — where each field selector maps to at most one element, so fingerprint-and-heal is an unambiguous 1:1. This composes cleanly with the zero-records escalation trigger: a single-record run always yields one record, so it never escalates, and the same healer is simply forwarded to whichever tier runs. **Still deferred to follow-on slices** (noted, not built here): **`item`-mode healing** (many rows share one selector, needing a per-row matching strategy rather than a single fingerprint); **cross-run re-anchoring** (rewriting a healed field's fingerprint so a subsequent redesign heals from the most recent shape, not only the first); and the **perceptual-hash-on-cropped-screenshot** component from the tier table (needs the browser tier's screenshot). The §5.3 mutation corpus is unchanged and stays green at ~99.8% (this slice adds no new scoring logic — only wiring around the existing engine). **Interaction with the §2b/§2c capture opt-in:** fingerprint persistence is *always-on* and independent of that opt-in — a plain run learns fingerprints so a future run can heal, whether or not the run captured a HAR/console/etc. It writes only to the `fingerprints/` subdir of the cache root, never a run-stamped capture dir. The existing "capture is off → nothing is written" scenarios (`capture.feature`, `signals.feature`, `accessibility.feature`, `response_headers.feature`, `storage_state.feature`) assert, per their Gherkin, that no *capture artifact* is written; their step glue was tightened-then-loosened to tolerate that one always-on `fingerprints/` subdir while still asserting no capture file appears — the honest claim, since a fingerprint is not a capture.

**Decision — Phase-3 tier-3 item-mode slice (field-within-row healing).** The third Phase-3 slice lands the first of the follow-ons the wiring slice deferred: **`item`-mode healing**, scoped deliberately to **healing a field selector that breaks *within* rows the `item` selector still matches** — not the row container itself. In a listing, each field's selector resolves relative to each matched row; when such a field's selector later matches nothing inside the rows (a class rename in a redesign) but the rows still match, tier 3 re-resolves the field **per row**, scoring the candidate elements within that row's subtree against the field's fingerprint. Three design choices make this correct and keep it generic (§0). (1) **Text-agnostic fingerprints.** A listing's rows are structurally identical but differ in text row to row, so text is per-row *noise*, not field identity — an item-mode fingerprint is captured with empty text (`fingerprint(element, include_text=False)`), so the scorer skips the text signal and matches on tag, id, class, other attributes, and structural position, all constant across the rows. (This is why the single-record path keeps `include_text=True`: there, text is a strong, stable anchor.) (2) **Namespaced cache key.** An item field is keyed `f"{item_selector}::{field_name}"` so a listing's `price` never collides with a single-record `price`, or another listing's. (3) **Prior-run-only healing.** `attempt` heals only against a fingerprint a *prior* run persisted (`FingerprintCache.get_persisted`, a load-time snapshot), never one `remember`ed earlier in the *same* run. This is the load-bearing rule that stops fabrication: a row that legitimately lacks an optional field finds no prior print of its own to heal from mid-run, so it stays null rather than being filled in from a sibling row that happened to have the field. Reliability-first holds unchanged (§2, §1): a confident per-row match fills that row's field; a sub-threshold best candidate is a flagged uncertain match and the field stays null. **Scope / still deferred:** healing the **`item` selector itself** when a row container breaks (total data loss for that row) needs a cross-row-invariant matching model plus group resolution and is *not* built here — a row that stops matching `item` is simply not extracted; **cross-run re-anchoring** and the **perceptual-hash-on-cropped-screenshot** component remain deferred as before. The §5.3 mutation corpus is unchanged and stays green (this slice adds no new scoring logic — only the `include_text` flag and per-row wiring around the existing engine).

**Decision — Phase-3 tier-3 re-anchoring slice (heal to the most recent shape).** The fourth Phase-3 slice lands **cross-run re-anchoring**, the follow-on the earlier notes deferred. The problem: fingerprints are captured on a successful resolve and persisted, so one redesign is healable — but markup drifts over *many* redesigns. If tier 3 only ever healed against the *first* shape it recorded, a second redesign that moved the element further from that original would eventually fall below the confidence threshold and stop healing, even though each individual redesign was a small, healable step. The fix is one line of behavior: when `Healer.attempt` heals a field **confidently**, it re-anchors — `cache.put(key, fingerprint(healed, include_text=…))` rewrites the stored fingerprint to the healed element's *current* shape, so the next run heals from the most recent shape and drift is absorbed one healable step at a time. It respects the same `item_selector`-derived `include_text` choice as capture, so an item-mode re-anchor stays text-agnostic. **Reliability-first (§2, §1):** only a *confident* heal re-anchors — an uncertain match never overwrites the good anchor with a guess (the same `0.6` bar that fills the field also gates the re-anchor, so we re-anchor exactly when we already trust the heal enough to use it). **Honest tradeoff, recorded:** re-anchoring means confidence compounds — a confident heal becomes the next run's truth, so a confident-but-wrong heal would drift the anchor. This is accepted deliberately: the alternative (a fixed original anchor) guarantees unbounded drift eventually breaks healing outright, whereas re-anchoring degrades gracefully and is bounded at each step by the same confidence gate. **Interaction with the same-run snapshot:** the re-anchor is a `put` (into `_store`, persisted at run end), visible only to a *future* run's `get_persisted` load-time snapshot — it does not change what other fields or rows heal against within the same run, so the item-mode fabrication guard from the previous slice is untouched. In item mode, all confidently-healed rows write the same text-agnostic fingerprint, so `put` no-ops after the first — no cache churn. **Still deferred:** healing the `item` selector itself when a row container breaks, and the **perceptual-hash-on-cropped-screenshot** component (needs the browser tier's screenshot). The §5.3 mutation corpus is unchanged and stays green (no new scoring logic — only a write-back in the orchestrator).

**Decision — Phase-3 tier-3 fingerprint-enrichment slice (descendant-composition signal).** The fifth Phase-3 slice is deliberately split off *ahead of* row-container healing (below), because that healing has a fabrication risk the existing fingerprint cannot defend against, and the fix is a pure scoring-core change worth landing and re-validating on its own. The problem: the `ElementFingerprint` was **leaf-oriented** — tag, id, class, attrs, inner text, and structural position (ancestor chain + sibling index). That is exactly right for a field element, but a *container* (a listing row, a card) has almost none of it that discriminates: its identity lives in *what it contains*. Two repeating same-tag sibling groups on a page — a product-listing `li` and a nav `li` — can look nearly identical to a leaf fingerprint once a redesign renames the container's class, so healing the row container against it could confidently resolve to the wrong group and fabricate records. The enrichment adds a **descendant-composition** signal: `ElementFingerprint.descendants` is the multiset of the element's descendant tag names (a sorted `(tag, count)` tuple), scored by a weighted-Jaccard `sum(min)/sum(max)` over the tag union (`_multiset_similarity`), weighted `_W_DESCENDANTS = 2.0`. **Leaf scoring is unchanged by construction:** the signal is applicable *only when the stored element had descendants* (the same "weighted mean over applicable signals" rule the other optional signals already follow), and a leaf field has none — so a heading or price span is scored exactly as before, and the §5.3 corpus (whose target `p-33` is a childless `<a>`) is untouched, re-validated green at **100% (300/300)**. Persistence is backward-compatible: a cache entry written before this slice has no `descendants` key and loads as an empty multiset (a leaf), so old per-domain caches keep working. This slice adds **no BDD scenario**: it is internal scoring-engine machinery with no user-observable behavior change on its own (leaf healing is identical; nothing yet heals a container), so it is covered by unit tests (`tests/test_healing.py`) and the mutation corpus per the test-pyramid split — the observable behavior it enables ships with the next slice, which does add a `.feature`. **Still deferred:** row-container/`item`-selector healing built on this signal (next slice), and the **perceptual-hash-on-cropped-screenshot** component (needs the browser tier's screenshot).

**Decision — Phase-3 tier-3 row-container-healing slice (heal the `item` selector).** The sixth Phase-3 slice lands the last of the item-mode follow-ons: healing the **row container** — the `item` selector itself — when a redesign breaks it so *no* rows match and the listing suffers total data loss (distinct from the item-field slice, which heals a field breaking *inside* rows the `item` selector still matches). It is built directly on the descendant-composition signal, which is what makes it safe: a leaf-oriented print could not tell a product row from a nav item once the container's own class was renamed, so healing a container against it risked confidently resolving to the wrong group and **fabricating records**. Two design choices keep it honest (§2, §1, §0). (1) **A repeating-group model, not a single best element.** A listing is by nature a repeating group of structurally-identical siblings, so `find_container_groups` (pure, in `healing.py`) scores every element text-agnostic against the container fingerprint, keeps those at/above threshold, and groups them into *coherent sibling groups* — same parent element **and** same tag — retaining only groups of **two or more** members. `Healer.attempt_container` heals only when **exactly one** group qualifies (returning its rows and re-anchoring the container print to the first row's current shape, as fields do); it **refuses** otherwise. (2) **Two refusals, both reliability-first.** Zero qualifying groups — a lone confident look-alike with no repeating group — is refused (a single stray element is never promoted into a fabricated one-row listing, the *≥2-member gate*); two-or-more qualifying groups — two distinct coherent groups both surviving the redesign confidently — is refused as *ambiguous* (tier 3 cannot know which group the config meant, and better zero records than a confidently-wrong listing). Either refusal leaves the listing with no records and records an **uncertain** `HealEvent` so the run summary flags it for review (§2d), never a silent empty result. The container fingerprint is captured **text-agnostic** and keyed by a sentinel empty field name (`f"{item}::"`, which no real — always non-empty — field key can collide with), and healed only against a **prior-run** print (`get_persisted`) — the same fabrication guard the item-field slice established. Wiring is one branch in `extract_records`: when `item` matches, remember the first row's container shape; when it matches nothing, attempt a container heal and extract from the healed rows if one group was confident. This composes with the zero-records escalation trigger unchanged — a confident heal yields records (no escalation), a refusal yields zero (escalates to the browser tier, which re-renders and re-attempts generically). The §5.3 mutation corpus is unchanged and stays green (this slice adds grouping/decision logic around the existing per-element `score`, no new scoring math). **Still deferred:** the **perceptual-hash-on-cropped-screenshot** component (needs the browser tier's screenshot) — now the only remaining tier-3 follow-on.

**Decision — Phase-3 tier-3 perceptual-hash slice (visual signal on a cropped screenshot).** The seventh Phase-3 slice lands the **last** tier-3 component from the §2 tier table — "DOM fingerprint + attribute similarity + perceptual-hash on a cropped screenshot, no model call" — completing tier 3. It exists for a specific gap: a **leaf element carrying almost no inner text** (an icon, a logo, an image thumbnail) has a thin DOM identity (tag, a class or two, structural position), so a class rename plus an attribute churn in a redesign can drop its DOM-only heal below the confidence bar even though it re-renders pixel-for-pixel the same. The perceptual hash of its cropped screenshot is exactly the identity that survives that churn. **The engine (`spoor/core/visual.py`), from scratch.** A **difference hash (dHash)**: decode the PNG, convert to grayscale, resize to 9×8, and emit one bit per adjacent-pixel comparison per row → a 64-bit hash; `visual_similarity` is `1 - hamming_distance/64`, in `[0,1]`. It is not template matching — it needs no OpenCV — so the §7 tier-3 table's OpenCV row is **not** taken up by this slice: it is **substituted** by Pillow + numpy (decode/resize + the bit math), a lighter, local-first dependency that keeps the from-scratch, deterministic-by-default ethos. OpenCV stays a *deferred* dependency for if/when actual template matching is built (recorded in the §7 table). **Documented caveat:** dHash keys off gradients, so a flat/solid-colour crop has no gradients and hashes to 0; the signal earns its keep on visually-structured elements (logos, photos, icons), which is exactly where a thin-DOM leaf needs it. **Blending, in the same weighted score.** `ElementFingerprint` gains `visual_hash: int | None` (default None; every pre-slice cache entry and every DOM-only print loads as None). The visual signal is weighted `_W_VISUAL = 2.0` and — unlike the other optional signals, which gate on the *stored* print alone — applies **only when both the stored print and the candidate carry a visual hash**, because a candidate's hash is computed on demand (a screenshot) only for a few front-runners at heal time, not for every element. **Heal-time re-rank, bounded.** `heal` gains a `visual_lookup` callback; when the stored print has a visual hash and a lookup is supplied, the top `_VISUAL_RERANK_K = 5` DOM front-runners are re-scored with the visual signal blended in and the field re-sorted — at most ~5 screenshots per heal. Without a visual hash or a lookup it is a pure DOM heal, byte-for-byte as before. **The parsel↔live-page bridge.** Extraction runs on the `parsel` tree parsed from `page.content()`, but a screenshot needs the live Playwright page; the browser tier bridges them by computing the element's absolute lxml XPath (stable across that identical serialization) and screenshotting it through a Playwright `xpath=` locator, then perceptual-hashing the PNG. The `Screenshotter` is bound to the `Healer` for the duration of live-page extraction and cleared after, so it never outlives the page. Purely **opportunistic (§2c)**: a hidden, zero-size, unlocatable, or un-decodable element yields None (no visual signal), never an error that fails the extraction. **Two-step contract, unchanged:** the healer re-resolves the *element*; `_value_from_element` extracts the value — a confident visual heal to the right element still yields a null value if the field's `attr` isn't present, and is still counted a confident heal. **Reliability-first (§2, §1):** the visual signal is a **corroborator, not a blanket boost** — a matching appearance lifts a DOM-uncertain match to confident, but a genuinely changed appearance withholds, leaving the match uncertain and the field null. `features/self_healing_visual.feature` drives the **real** browser tier against a live loopback server over two runs sharing one temp per-domain cache (calibrated so the DOM-only heal lands ~0.58, below the 0.6 bar, and an identical appearance lifts it to ~0.70). The §5.3 mutation corpus is unchanged and stays green (the corpus heals DOM-only — no `visual_lookup` — so the new blend never engages there). Nothing is site-specific (§0): the same bridge and hash run for every target. **This completes Phase-3 tier 3** — no tier-3 follow-ons remain.

## 2a. The user-facing interface: declarative extraction configs

**Two distinct modes, not two more rungs on the same ladder.** §2a and §2e are easy to conflate — both walk pages, both mention "signals" — but they're different operating modes with very different cost profiles, not points on one escalation path. §2a (this section) is **cheap and targeted**: extract named fields from a target whose shape you already know; one run costs roughly what the resolution tiers cost per configured field. §2e is **heavy and exploratory**: discover and traverse a target's entire actionable surface with no prior config, capturing a full signal bundle at every step; a run's cost is proportional to the size of the whole state graph, not one field. Use §2a when you know what you want; use §2e when you want to find out what's there.

Everything so far is internals. There's a gap worth closing: how does someone actually *tell* the tool what to extract? The answer that keeps the "essential, not tailored" principle intact is a declarative config file, not per-target Python — the schema shape is identical for every target, so pointing the tool at a new site is writing a new config, never new code:

```yaml
target: https://example.com/products
fields:
  title: { selector: "h1.product-title" }
  price: { selector: ".price", type: number }
  availability: { selector: ".stock-status" }
pagination:
  next: "a.next-page"
```

Each field's `selector` is just the tier-1 starting point — the escalation dispatcher (§2) still walks it through tiers 2–4 automatically if tier 1 fails, so the config author never writes tier-specific logic. `pagination.next` (or an `infinite_scroll: true` flag) tells tier 4 when to keep going and, just as importantly, when to stop. A thin CLI (`spoor run config.yaml -o output.json`) is the whole product surface on top of this — config in, structured data out.

**Single record vs. repeating records (decided).** The example above extracts one record per page (the fields resolve against the whole document). The far more common scraping shape — a listing page with many rows — is expressed by one optional key, `item`, a root selector that matches each repeating record; when present, every field's `selector` is resolved *relative to* each matched `item` element, and the run emits one output record per match instead of one per page. When `item` is absent, behavior is exactly the single-record case above (fields resolved against the whole document), so existing single-record configs are unaffected. This composes with pagination the obvious way: for each page, extract all `item` matches, then follow `pagination.next`. The `item` selector is itself just a tier-1 starting point, escalated the same as any field selector — the config author still never writes tier-specific logic. Example:

```yaml
target: https://example.com/products
item: "li.product-card"          # one output record per match
fields:
  title: { selector: "h2.title" }      # resolved within each product-card
  price: { selector: ".price", type: number }
pagination:
  next: "a.next-page"
```

**Text vs. attribute values (decided).** By default a field takes the selected element's normalized text. A field's data often lives in an **attribute**, though — a link's `href`, a fuller `title`, an `<img>` `src`, a `data-*` value. That's expressed by one optional key on a field, `attr`: when set, the named attribute's value is taken instead of the element text; when absent, behavior is exactly the text case above, so existing configs are unaffected. `type` coercion (e.g. `number`) applies either way, and the selector is escalated the same as any field selector. Example: `full_title: { selector: "a.product-link", attr: title }`.

## 2b. API surface discovery (runs alongside the UI tiers, not a separate crawl)

The goal here isn't just "find some API calls" — it's building up, over time, as complete a picture as can honestly be observed of what a product's API surface is and how the UI actually uses it. **Bounded claim, stated plainly:** this is inference from what was exercised, not guaranteed-exhaustive discovery — official spec discovery (layer 1) is authoritative when it succeeds, but GraphQL introspection can be disabled, and layers 3–5 only ever see endpoints a run actually happened to trigger. Spoor's API surface report means "everything observed so far," not "everything that exists" — worth stating exactly that way in user-facing docs, never softened into "the entire API surface." That decomposes into four layers, ordered cheapest/most-certain first:

1. **Official spec discovery (near-free).** Before anything else, probe a short list of conventional paths (`/openapi.json`, `/swagger.json`, `/api-docs`, `/.well-known/openapi.json`) and scan page HTML/JS bundles for references to one. If a real OpenAPI/Swagger doc exists, use it directly — no reverse-engineering needed, and it's authoritative.
2. **GraphQL introspection (also near-free, when available).** If a `/graphql`-shaped endpoint turns up, a single standard introspection query returns the entire schema. Many production APIs disable introspection deliberately, so this is opportunistic, not guaranteed.
3. **Passive traffic capture as a side effect of every tier 1–2 run.** Since the whole stack already drives real browser sessions via Playwright, network capture is nearly free: Playwright can record a HAR file natively for any context (`record_har_path`), with no separate proxy or CA-certificate install needed (that hassle only matters for non-browser traffic, which is out of scope now). Every scraping run silently accumulates the real requests the UI actually made.
4. **Spec synthesis from accumulated captures — needs answering before Phase 2.5, see §9.** Plainly: once Spoor has recorded a pile of raw API calls (from step 3), something has to turn that pile into an actual readable API spec — recognizing that `/users/1`, `/users/2`, `/users/3` are really "the same endpoint, `/users/{id}`, with different IDs," and writing that out as an OpenAPI document. The open-source **mitmproxy2swagger** project already does exactly this clustering/inference. The open question is purely mechanical: mitmproxy2swagger expects its input in mitmproxy's own "flow" file format, not the HAR format Playwright natively produces (§2b step 3) — so it's unconfirmed whether HAR can be fed into it directly or converted cleanly (mitmproxy itself gained HAR support in version 10.1, which may bridge the two formats, but that hasn't been verified against this actual tool). This needs a short hands-on spike — try feeding it a real HAR file — before Phase 2.5 is scoped for real; if it doesn't work cleanly, the fallback is writing the same clustering logic directly against HAR, which is a well-understood, bounded piece of work either way.
5. **Action-to-endpoint correlation — the one genuinely custom piece.** None of the above tools tell you *which UI action triggered which API call*, and that's the "find the use of those APIs" part of the ask. This just needs a lightweight checkpoint log: before each simulated action (click, scroll, form submit), mark a timestamp; afterward, attribute any requests captured in that window to that action. Over many runs this turns a flat list of endpoints into "here's what this endpoint is *for*." **This is an approximation, not exact causal attribution** — background polling, prefetch requests, or analytics beacons that happen to fire inside the same window get attributed to the action too. Read any single correlation as "likely caused by," not proven; over many runs the noise mostly averages out, but the map should never claim exact click-to-call certainty.

None of this needs an LLM or a new dependency beyond mitmproxy2swagger (MIT-licensed) — it's a natural, nearly-free companion to tiers 1–2 rather than a fifth automation surface. **On relying on the synthesized spec:** treat it as a strong starting point for understanding a product's surface, not a guaranteed-accurate contract — always verify before building anything (a test, an integration) that depends on it being complete or correct.

**Decision — §2b layer-1 first slice (official spec discovery).** The cheapest, most-certain layer ships first, on its own: **conventional-path probing**. Alongside every run (`run_report`, not a separate crawl), Spoor probes a short, fixed list of conventional spec paths against the target's origin — `/openapi.json`, `/swagger.json`, `/api-docs`, `/.well-known/openapi.json` — and treats the first that returns `200` with JSON carrying an `openapi` key (→ OpenAPI 3.x) or a `swagger` key (→ Swagger 2.0) as a discovered spec, recording its kind, version, and URL. Anything else (404, non-JSON, JSON without a version key — e.g. a SPA's `/api-docs` HTML shell) is *not* a spec: probes must not produce false positives. Deliberately scoped for this slice, and deferred (not dropped):

- **Default-on, robots-respecting, bounded — and crawl-delay-exempt.** The probes run on every scrape (§2b: "before anything else, probe…"; passive, near-free). They honor `robots.txt` allow/deny — a disallowed path is not probed (§6; we never work around a disallow to find a spec) — and are capped at the fixed path list. They are, however, **exempt from crawl-delay spacing**: this is a one-time origin probe of ≤4 conventional paths, not the repeated page crawling a crawl-delay guards against, and applying the delay would turn a "nearly-free" companion into a multi-second per-run tax (and did — it broke the extraction crawl-delay contract, exactly the signal that discovery had become a hidden cost). Allow/deny is respected; the delay is not applied to the probe set. Probe failures are swallowed: "no spec observed there", never an error that fails the run.
- **`code`-level generality (§0).** The path list and the version-key check are conventions identical for every target — no site knowledge. Discovery lives in `spoor/api_discovery/`, outside `core/`.
- **Bounded claim in the output.** The run summary reports a discovered spec as *observed*, never as "the complete API" — matching §2b's stated bounded claim.
- **Deferred to later §2b slices:** ~~GraphQL introspection (layer 2)~~ (shipped), ~~passive-capture spec synthesis (layers 3–4, gated on the mitmproxy2swagger spike)~~ (layer-3 HAR capture and layer-4 synthesis both ship — see the layer-4 note), and ~~action-to-endpoint correlation (layer 5, the one remaining layer)~~ (layer 5 ships — see the layer-5 note; all five §2b layers are now in place). Layer 1 itself is now complete — both conventional-path probing and reference-scanning (landing HTML *and* same-origin JS bundles) ship (see the next note). Also deferred: sharing one robots cache / politeness gate between the resolver and discovery (today each builds its own, so a run fetches `robots.txt` twice) — a bounded, known optimization, not a correctness gap.

**Decision — §2b layer-1 second half (spec references in the landing HTML and its JS bundles).** When conventional-path probing finds nothing, the run now fetches the landing page and scans for a *reference* to a spec — first in the landing HTML, then inside the same-origin JS bundles the page loads — then probes each candidate. References are found generically (§0): Redoc's `spec-url` attribute, and any quoted, whitespace-free token carrying the spec vocabulary (`openapi`/`swagger`/`api-docs`) — which covers a Swagger-UI `url:` config, a `<link>`/`<a href>`, or an inline path. Candidates are resolved against the landing page's *final* URL (after any redirect), de-duplicated, and **capped** (`_MAX_HTML_SPEC_CANDIDATES`) to stay bounded and near-free. The reference-finding is deliberately *loose* because the **validation is strict**: every candidate goes through the same JSON `openapi`/`swagger`-version-key check as a conventional probe, so a false lead (a `swagger-ui.html` shell, an unrelated `.json`) costs one bounded fetch and is rejected, never reported — probes must not produce false positives (same guarantee as the first half). **JS-bundle scan specifics:** only *same-origin* `<script src>` bundles are fetched (a spec's config usually lives in the app's own bundle; fetching arbitrary third-party origins would be neither bounded nor polite), capped at `_MAX_SCRIPT_BUNDLES`, and a reference found in a bundle is resolved against the *document* URL, not the script's — matching how a browser resolves a bundle's own relative `fetch`. Same non-negotiables carry over: `robots.txt` allow/deny is honored on the landing fetch, each bundle fetch, and each probed candidate (§6); the probes are crawl-delay-exempt; every failure is swallowed into "not there"; and a hit is reported as *observed*, never a complete-API claim. Deliberately scoped, deferred (not dropped): **cross-origin JS bundles** (same-origin only for now); **YAML specs** (validation stays JSON-only, matching the conventional paths — a YAML-referenced spec is found but fails the JSON check for now). Known cost, accepted for this slice: on a conventional-path miss the run fetches the landing page again (the resolver already fetched it), the same bounded double-fetch already noted for `robots.txt` above — reusing the resolver's HTML is the deferred optimization.

**Decision — §2b layer-2 slice (GraphQL introspection).** Alongside every run, and in the same shape as layer-1 probing, Spoor probes a short fixed list of conventional GraphQL endpoints (`/graphql`, `/api/graphql`) with a single standard introspection query (POST). An endpoint that answers `200` with `data.__schema` present has introspection enabled; Spoor records the endpoint URL and the number of types the schema reports (proof it was observed, and a cheap size signal). Anything else — 404, a non-GraphQL 200 JSON, a `200` whose body is all `errors` with introspection disabled — is not a discovered schema, so it never false-positives. Same guarantees as layer 1: generic (§0; the endpoint list and the introspection query are identical for every target, and `spoor/api_discovery/` sits outside `core/`); honors `robots.txt` allow/deny but is crawl-delay-exempt (a one-time bounded probe); every failure swallowed into "none observed"; reported as *observed*, never a complete-API claim. **Opportunistic, not guaranteed** — §2b already states many production APIs disable introspection deliberately, so a "none" here means "not observed / not exposed", never "no GraphQL exists". Deliberately scoped: this slice records the endpoint + type count, not the full schema document; **persisting the raw introspection result to the local-only cache (§2h), and full type/field detail, are deferred** to a later slice.

**Spike finding — §2b item 4: mitmproxy2swagger accepts a Playwright HAR directly (open question resolved).** The §9 open question — mitmproxy2swagger was documented as expecting mitmproxy's own "flow" format, not HAR — is resolved by a hands-on spike (mitmproxy2swagger 0.15.0). The tool now has native HAR support: a `-f har` input format and a `HarCaptureReader` that reads standard HAR 1.2 (`log.entries[].request.url/method/headers`, `response.status/content`). Fed a **genuine Playwright HAR** (creator `Playwright/1.62.0`, produced by the same `record_har_path` the §2b step-3 capture uses) covering `/api/users/1`, `/api/users/2`, `/api/users/3`, `/api/products/10`, it clustered them into `/users/{id}` and `/products/{id}` and emitted valid OpenAPI 3.0.0 with response schemas inferred from the bodies. **So the "flow-format conversion step" that §7 lists mitmproxy for (`Optional, spike-dependent`) is not needed — mitmproxy proper is not a required dependency for this path.** Caveats the spike surfaced, to design around at Phase 2.5 scoping (none is a blocker):
- **Drive it as a library, not the CLI.** The CLI is interactive by design — a first pass writes discovered endpoints under `x-path-templates` each prefixed `ignore:`, expecting a human to un-comment the wanted ones before a second pass emits real paths. An automated pipeline would strip that prefix between passes (the spike did) — or, cleaner, skip the CLI and drive `HarCaptureReader(...).captured_requests()` + the path-templating directly, which also sidesteps the next two caveats.
- **Windows console-encoding crash in its CLI.** The CLI writes a Unicode progress bar (`▌`) to stdout and crashes under cp1252 (the default Windows console), then its broad `except` mislabels the crash as "Failed to parse the input file as 'har'" — a red herring; parsing had actually succeeded. This is the same cp1252 hazard §2d's `RunSummary.render` already avoids with ASCII. Forcing UTF-8 stdout works around it; driving the library API avoids the progress callback entirely.
- **Force `-f har`; don't rely on auto-detection.** A Playwright HAR's creator is `Playwright`, not `WebInspector`/`Firefox`, so the tool's format heuristic scores it 103 rather than its max. Since Spoor always knows its own input is HAR, pass the format explicitly.
- **Dependency weight is real, and reframes the §9 fallback as a live choice.** Installing mitmproxy2swagger pulls a heavy transitive tree (mitmproxy, Flask, tornado, aioquic, ldap3, urwid, and a `cryptography` **downgrade** 50→48) for what is fundamentally URL-clustering over a ~120-line HAR reader. So the §9 fallback — "write the clustering logic directly against HAR" — is now worth weighing as a possible *preferred* approach, not merely a contingency: it would avoid the mitmproxy dependency and the two caveats above entirely. Which way Phase 2.5 goes (depend on mitmproxy2swagger as a library vs. reimplement the bounded clustering against HAR) is a scoping decision for that phase, recorded here but **not decided by this spike**. The spike's job was only to answer "does HAR feed in cleanly?" — it does.

**Decision — §2b layer-4 slice (spec synthesis from captured HAR), and the library-vs-reimplement fork resolved (maintainer decision).** The fork the spike left open is decided: **reimplement the bounded URL-clustering directly against HAR, rather than depend on `mitmproxy2swagger`.** Rationale, per the spike's own reframing above: the synthesis is fundamentally URL-clustering over the HAR Spoor already captures, and taking the library would pull a heavy transitive tree (mitmproxy, Flask, tornado, aioquic, urwid) plus a `cryptography` **downgrade** 50→48, and drag in the two Windows/CLI caveats, for a piece that is small and well-understood. So `mitmproxy2swagger` is **not** a Spoor dependency; §7's row for it stays "Not needed". First slice, deliberately tight:

- **Reads the run's own captured HAR, no network.** When a run captured a HAR (`capture.har: true`, so `har_path` is set), synthesis reads that file and clusters it — it is a pure local-file → spec step, adds no request, and honors nothing network-side because it touches no network. Never raises: an unreadable/absent/invalid HAR, or one with no API entries, yields "nothing synthesized" (None), the same swallow-into-none discipline as layers 1–2.
- **Generic clustering only (§0).** Entries are kept when the response is JSON (`mimeType` carries `json`) and same-origin with the target (the layer-1 same-origin precedent; cross-host/subdomain API surfaces are **deferred**, not dropped). Path templating replaces ID-like segments with `{id}` by a fixed, generic rule — all-digit segments, UUIDs, and long (≥24-char) hex (Mongo-ObjectId shape) — chosen **conservatively**: over-clustering (collapsing two genuinely distinct paths) misrepresents the surface worse than under-clustering, so a borderline segment is left literal. Entries are grouped by `(method, templated path)`, each endpoint carrying the sorted set of observed status codes. Output is sorted `(path, method)` for determinism. No site knowledge anywhere; the module lives in `spoor/api_discovery/`, outside `core/` (the run wiring in `core/` carries no site logic, only the call).
- **§2h — the synthesized doc is local-only, counts only in shared output.** The synthesized OpenAPI 3.0 document is written to the run's local-only cache dir (beside the HAR, `synthesized_openapi.json`), exactly like the raw captures; the run summary surfaces only **counts** (endpoints synthesized, requests clustered) plus that local path — never the templated path list. Rationale identical to the header-value deferral (§2c): a synthesized path can embed an un-clustered secret segment (a reset token the ID rule didn't match), and surfacing derived paths to shared output is a redaction decision, so it waits for a later slice rather than being made ad hoc here. The doc *is* produced and usable from the cache today; only its promotion to shared output is deferred.
- **Bounded claim, unchanged.** A synthesized spec is inference from what a run happened to exercise (§2b's stated bound for layers 3–5) — reported as *synthesized from observed traffic*, never "the complete API". **Deferred (not dropped):** response/request **body schema inference** (mitmproxy2swagger did this; this slice records methods + status codes only), **query-parameter modelling**, **cross-host** surfaces, **YAML output**, and **accumulation across runs** (this slice synthesizes from the current run's HAR; §2b's "accumulated captures over time" is a later slice). A known consequence of the JSON-response filter, accepted for this slice: an API response with **no JSON body** (a `204 No Content`, a redirect, a non-JSON payload) is not captured, so a state-changing endpoint that answers that way is currently missed — the filter is deliberately conservative to keep static assets (HTML/CSS/JS) out, and widening it (e.g. denylist static types instead of allowlist JSON) is a later refinement. ~~Layer 5 (action-to-endpoint correlation) remains the last §2b layer.~~ Layer 5 now ships too (see the next note) — §2b's five layers are all in place.

**Decision — §2b layer-5 slice (action-to-endpoint correlation), the last §2b layer.** The one genuinely custom piece (§2b item 5): none of layers 1–4 tell you *which UI action triggered which API call*. This ships as the lightweight checkpoint log §2b describes: the browser tier marks a timestamped checkpoint before each simulated action — one `"load"` before every `page.goto`, one `"scroll #N"` before each infinite-scroll step — and afterward each captured request is attributed to the action whose window it fell in (the last checkpoint at or before the request's `startedDateTime`). This is `spoor/api_discovery/correlation.py`; the browser wiring in `core/` carries only the marking calls, no site logic (§0). First slice, deliberately tight:

- **Reuses the layer-3/4 HAR primitives; generic (§0).** Correlation reads the run's own captured HAR (no network, never raises — an unreadable HAR, no checkpoints, or nothing attributable yields None, the same swallow-into-none discipline as layers 1–4) and applies the *same* same-origin + JSON filter and the *same* generic ID-templating as layer 4 (it imports them, so the two layers can never drift). A request is attributed by timestamp only — a `bisect` onto the sorted checkpoint times — so nothing is site-tailored. Checkpoints are marked only when a HAR is being captured (nothing to correlate against otherwise).
- **Approximation, not proof — stated in the output (§2b).** A time window catches whatever fired in it: background polling, prefetch, and analytics beacons that land in the same window are attributed to the action too. The correlation is reported and documented as *likely triggered by*, never proven causation — the local-only document carries an explicit `note` saying so, and the summary line is worded "requests likely triggered by N actions". Read any single correlation as "likely", per §2b's stated bound.
- **§2h — the correlation doc is local-only, counts only in shared output.** The per-action endpoint lists (templated paths) are written to the run's local-only cache (beside the HAR, `action_correlation.json`); the run summary surfaces only **counts** (requests attributed, actions credited) plus that local path — never the paths themselves. Rationale identical to the layer-4 deferral: a templated path can embed an un-clustered secret, so promoting derived paths to shared output is a redaction decision for a later slice.
- **Deferred (not dropped).** The in-vivo browser scroll→fetch correlation is **not** yet exercised end to end: `feed.html` scrolls by appending DOM synchronously (no network), and the `live_server` fixture serves static files only, so a real scroll-triggered-fetch scenario needs a **new network-driven feed fixture** and carries real-browser timing-window flakiness — scoped as a follow-up. These scenarios drive the pure correlation engine directly (synthetic checkpoints + a captured HAR), which is where the attribution logic lives. Also deferred: **richer action types** (clicks, form submits — §2b names them; today only load + scroll are the actions the crawl actually performs, so those are what get marked), **accumulation across runs** (§2b's "over many runs the noise averages out" — this slice correlates within one run), and the same **cross-host** and **body-schema** bounds layer 4 already defers.

## 2c. Additional signals catalog

Beyond DOM/selectors and the API surface, a Playwright session already sits in a position to observe a lot more about a product with little or no extra machinery. Grouped by cost, so it's clear what's "on by default" vs. opt-in:

**Free / near-free — capture these by default alongside the HAR file (Phase 2.5):**
- **Client-side storage**: `localStorage`, `sessionStorage`, IndexedDB, cookies via `context.storage_state()` — often reveals feature flags, cached responses, and auth tokens never visible in the DOM.
- **Console output & JS errors**: `page.on("console")` / `page.on("pageerror")` — developers leak surprisingly informative debug output and stack traces in production more often than expected.
- **Accessibility tree**: `page.accessibility.snapshot()` — a structural view independent of visual markup; doubles as a resilience signal for tiers 1/3, not just extra data.
- **Response headers**: CSP, CORS, server/infra headers — cheap fingerprint of backend tech and security posture, already flowing through the HAR capture.

**Cheap — a bit of CDP wiring, still no new dependency:**
- **WebSocket / SSE frames**: `page.on("websocket")` — HAR-based capture misses push-based traffic entirely (chat, live dashboards, trading UIs), so this matters a lot for real-time products.
- **Performance metrics**: CDP `Performance.getMetrics` — JS heap size, DOM node count, layout/recalc counts; useful for spotting unusually heavy pages or regressions across versions.
- **Service worker cache contents**: reveals what the app pre-caches, i.e. what it expects to need.
- **Third-party script inventory**: analytics/support/payment scripts loaded — a fingerprint of what vendors the product integrates with.
- **Computed styles**: sampled across elements, can reconstruct a design system (color/spacing/type tokens) when that's relevant.

**Expensive or invasive — opt-in flags, never part of a default run:**
- **Full session video recording** (`record_video_dir`) — great for human review or eval/training data, but storage-heavy; enable per-run, not per-default.
- **JS heap snapshots** (CDP `HeapProfiler`) — can surface in-memory app state (e.g. a Redux/Vuex store) that never gets serialized to the DOM or network, but it's slow and heavy; treat as an occasional deep-dive tool.
- **Media manifest / streaming capture**: `<video>`/`<audio>` element state (`currentTime`, `buffered`) plus HLS/DASH manifest requests — only relevant if the target is actually a media/streaming product.
- **Canvas/WebGL pixel capture**: the fallback of last resort for canvas-rendered UI (games, some dashboards) where there's no DOM/network signal underneath at all — lossy and only worth it when nothing else applies.

Same principle as the rest of the stack: default to what's already flowing through the session for free, and gate anything storage- or CPU-heavy behind an explicit flag so a routine scrape doesn't silently become a slow, disk-filling one.

### Decision note — §2c first signal: console output & JS errors (implemented)

The first signal built from this catalog is **console output & uncaught JS errors** (`page.on("console")` / `page.on("pageerror")`), captured on the browser tier. Decisions made in building it, to be reused as the remaining signals land:

- **Opt-in for now, via `capture.console`.** The catalog frames the free/near-free signals as default-on, but that's the full Phase-2.5 target; interim capture stays opt-in and parallel to `capture.har`, so a routine run's behavior is unchanged until default-on is switched on deliberately (one decision, one PR).
- **§2h split — raw local-only, counts shared.** Console output can carry secrets (tokens logged in debug output), so the raw per-message log is written to the local-only run cache (`console.jsonl`, alongside the HAR) and never routed to shared output. The run summary surfaces only non-sensitive **counts** (total messages, error-level messages, uncaught page errors). Surfacing message *content* to shared output is deferred until the §2h redaction pipeline exists — a count leaks nothing, a message might.
- **`page_errors` counted separately from `errors`.** An uncaught exception (`pageerror`) is a stronger "this page broke" signal than a `console.error`, so the two are tallied separately rather than merged.
- **One run directory per run.** All captures for a run (HAR, console log, and future signals) share a single `new_run_cache_dir()`, rather than each capture minting its own.

### Decision note — §2c second signal: accessibility tree (implemented)

The accessibility-tree snapshot follows the same pattern as the console signal, so the note above applies. Signal-specific decisions:

- **Read over CDP, not the old snapshot API.** §2c named `page.accessibility.snapshot()`, but Playwright removed it (>=1.55). The tree is instead read over the Chromium DevTools Protocol (`Accessibility.getFullAXTree`), which returns the full flat node list. This is Chromium-only — exactly the browser the tier runs — so it stays generic (§0). This nudges the signal from §2c's "free" tier toward its "a bit of CDP wiring" tier, but the cost is one CDP call per page: negligible.
- **Opt-in via `capture.accessibility`**, browser-tier only (a tier-1 fetch has no rendered tree to snapshot).
- **Raw trees local-only, node count shared.** The raw per-page trees (potentially large) go to the local-only cache (`accessibility.json`); the run summary carries only the total accessible-node count. The tree's accessible *names* are visible-label text (the same class of data the DOM already exposes to extraction), not credentials, so this isn't a secret-bearing capture like storage state — but the aggregate-only-in-shared-output rule is kept uniform across all signals regardless.
- **Node count as a resilience signal.** §2c frames the tree as doubling as a tier-1/3 resilience signal: a near-zero node count (e.g. a canvas-rendered UI) is an early warning that selector-based extraction will struggle, which is why the count — not just the raw tree — is the surfaced aggregate.

### Decision note — §2c third signal: response headers (implemented)

The response-header fingerprint (CSP, HSTS, X-Frame-Options, `Server`, `X-Powered-By`, CORS) follows the same opt-in, browser-tier, one-run-directory pattern. It forced the first §2c §2h fork the count-only signals (console, accessibility) had sidestepped, because for headers the *values* are the intelligence — and some headers (`set-cookie`, `authorization`) are known secret shapes. **Decision (user-confirmed): presence/counts only in shared output.**

- **Header values are never surfaced to shared output.** The raw full headers — all values, `set-cookie` included — are written to the local-only run cache (`headers.json`). The run summary carries only non-sensitive *derived* facts: the count of distinct header names, and presence booleans for the key security headers (CSP / HSTS / X-Frame-Options). This keeps the count-only line the earlier signals held and needs no secret-pattern redaction yet.
- **Value-surfacing is deferred to the §2h redaction slice.** Surfacing useful non-secret header values (e.g. `Server`, CSP contents) to shared output is worth doing, but it's exactly a redaction decision — an allowlist/denylist of header names is a form of the redaction pipeline — so it waits until that pipeline is built rather than being decided ad hoc here. The alternatives weighed were a curated fingerprint allowlist (rejected: makes the §2h call prematurely) and all-local-only (rejected: needlessly hides the posture signal).

### Decision note — §2c fourth signal: client-side storage state (implemented)

Client-side storage — the browser context's cookies + per-origin localStorage, via `context.storage_state()` — is the last free/near-free §2c signal and the first that *cannot* sidestep redaction: session cookies and localStorage tokens are themselves the sensitive data, so it is the deliberate forcing function for the §2h redaction pipeline (built first as its own slice — see the secret-redaction-pipeline note in §2h). Same opt-in (`capture.storage: true`), browser-tier-only, one-run-directory, off-by-default shape as the other §2c captures.

- **Raw local-only, redacted-entries shared.** The raw, unredacted storage state (every cookie and localStorage value) is written to the local-only run cache (`storage_state.json`) and never shared. The shareable `StorageStateSignal` carries non-sensitive counts (cookies / localStorage entries / origins) *and* the entries as redacted `name=value` strings: the name is kept (a structural signal — which cookies and storage keys the app uses), the value is passed through the §2h `redact` primitive. This is a genuine step past the header signal's counts-only line — real entries reach shared output — made safe by the now-existing redaction pipeline.
- **Why reconstruct `name=value` before redacting.** Redaction recognizes secret *shapes*; a bare cookie value (opaque hex) matches none. Reconstructing `name=value` lets the pipeline's cookie/auth-key rules fire on the name (`sessionid`, `access_token`, …) while its token-shape rules still catch a JWT/API-key value under any key. This is why the pipeline was built first — the signal consumes it rather than reinventing an ad-hoc scrub.
- **The residual risk is stated, not hidden.** Because storage entries *are* surfaced (values, redacted — unlike the header signal's counts-only), the known-shape boundary has teeth here: a secret value in no recognized shape, under an *unrecognized* name (e.g. a framework cookie like `laravel_session=<opaque>`), matches nothing and would reach shared output **unredacted**. This is consistent with §2h's own model — shared output is *known-pattern* redacted, and the raw full state (all values) additionally lives in the local-only cache — but §2h is explicitly not an entropy detector, so surfacing entry values accepts this residual. It is called out rather than implied-away. Mitigations if it proves too risky in practice (a per-target expansion of the recognized cookie/key names via the recognizers table, an opt-in entropy heuristic, or falling back to names-only for storage values) are deliberately deferred, not silently assumed.
- **Context-level capture.** Unlike the per-page console/a11y/header collectors, storage state spans pages, so it is captured once at the context level after the crawl (before `context.close()`), guarded so a capture failure never fails the extraction it rode along with.

This is also the §2h "bring-your-own-session" input surface (a supplied storage state is how authenticated targets are run); capturing and safely summarizing it is the read side of that same mechanism. The **input side is now implemented** — see the bring-your-own-session decision note in §2h.

## 2d. Operational essentials (the gap between "extracts data" and "usable tool")

These didn't come up earlier because they're not about *finding* an element — they're what makes the difference between a tiered-cascade demo and something people actually run unattended. All of them lean on existing libraries, same as everywhere else in the plan:

- **Politeness & rate limiting.** Crawlee's autoscaling pool already handles per-domain concurrency and backoff reasonably well for tiers 1–2, so most of this is configuration, not new code — but it should be a first-class `PolitenessPolicy` object (respects `robots.txt` crawl-delay, honors `Retry-After` headers, caps concurrent requests per domain) rather than just a README promise, since §6 already commits to respecting robots.txt by default.
- **Change detection.** Use `ETag`/`Last-Modified` headers or a content hash to skip re-processing pages that haven't changed since last run. This pairs directly with the per-domain cache already in §2 and is what makes monitoring-style use cases (price tracking, content-change alerts) cheap to run on a schedule instead of re-scraping everything every time.
- **CAPTCHA / anti-bot detection — detection, not bypass.** Recognize known challenge-page fingerprints (a Cloudflare interstitial's title text, a reCAPTCHA iframe) and fail loudly with a clear "blocked" result rather than looping forever or silently returning a challenge page as if it were data. An honest "hit a wall here" is itself a useful, expected output.
- **Retry and error classification.** Separate transient failures (timeout, 5xx, 429) from permanent ones (404, 410, confirmed block) — transients retry with backoff (the `tenacity` library, MIT-licensed, is a clean fit rather than hand-rolling this), permanents land in a dead-letter log for human review instead of vanishing silently.
- **Output pipeline.** Pluggable sinks downstream of extraction — JSON Lines, CSV, SQLite as the practical defaults (all stdlib or near enough), Parquet as an optional extra — with the field schema from §2a validated (via `pydantic`, already in the stack) before anything is written. Extraction without a usable output path isn't a finished tool.
- **Run observability.** A structured run summary — items scraped, how often each tier had to escalate, error counts, which fields fell back to tier 3/4 — so a user can tell whether a run actually went well without reading raw logs. This is the project's own signals-catalog thinking (§2c) turned inward on itself.
- **Proxy support hook.** A pluggable interface for user-supplied proxy lists/rotation (Playwright and httpx both accept per-request proxy config natively) — the project doesn't provide or endorse any proxy source, just a clean extension point, since real-world scraping at any scale usually needs one.

**Decision — Phase-1 output-pipeline slice.** The output pipeline (`spoor/operational/output.py`) is a first-class stage between extraction and disk, not a CLI afterthought. Its Phase-1 pass ships the dependency-free text sinks — **JSON, JSON Lines, and CSV** (all stdlib); SQLite and Parquet remain named §2d sinks for later. The format is chosen by inference from the `-o` file extension (`.json`/`.jsonl`/`.csv`), overridable by an explicit `--format`; an unknown extension with no `--format` is a clear error raised *before anything is fetched or written*. Per §2d, records are validated against a pydantic model built from the §2a config fields (correct field set, declared types, `extra="forbid"`) before any file is opened, so a schema violation aborts the whole write rather than leaving a partial file — and CSV columns are exactly the config's fields, in declared order.

**Decision — Phase-1 politeness slice and where the knobs live.** The politeness policy is a first-class object (`spoor/core/config.py:PolitenessPolicy` for the declarative knobs, `spoor/operational/politeness.py` for the runtime gate), configured per target via an optional `politeness:` block on the §2a extraction config — consistent with §2a's "a new site is a new config, never new code." Its Phase-1 scope is **respect `robots.txt` (default on, per §6) and honor the crawl-delay** (from robots.txt, or a `delay:` override in seconds). Fetching the `robots.txt` itself follows RFC 9309's conservative reading: an absent file (404) means no restrictions, but a server error (5xx) means the rules are unavailable and the origin is treated as disallowed rather than crawled as if open. Two parts of the §2d politeness bullet are deliberately deferred and are **not** a weakening of the commitment, only a phasing split: (1) *caps concurrent requests per domain* — the tier-1 crawl is sequential (one page, follow next-link), so a concurrency cap has nothing to bound until a request pool exists (tier-2 / Crawlee); (2) *honors `Retry-After` headers* — this only had meaning once a retry mechanism existed, and **has now landed** with the Phase-3.5 retry slice, living on `RetryPolicy` (`respect_retry_after`) rather than `PolitenessPolicy` since it is a retry concern (see the Phase-3.5 decision note below). Concurrency caps still slot into `PolitenessPolicy` when a request pool lands. Per §6, `respect_robots` may be set to `false`, but only as an explicit, deliberate opt-out — never the default.

**Decision — Phase-3.5 retry / error-classification slice (the deferred Retry-After lands here).** The retry mechanism the two notes above pointed forward to is a first-class object, split the same way as politeness: the declarative knobs live in `spoor/core/config.py:RetryPolicy` (an optional `retry:` block on the §2a config — `max_retries`, `backoff`, `respect_retry_after`), and the runtime lives in `spoor/operational/retry.py:RetryingFetcher`. Each tier-1 fetch outcome is classified by **generic HTTP category** (§0 — no site-specific wording): *transient* (timeouts, dropped connections, 5xx, 429) retries with exponential backoff (`backoff * 2ⁿ`); *permanent* (other 4xx) is taken at its word and not retried; success returns. This closes the item the politeness note deferred: a server-sent **`Retry-After`** (seconds or HTTP-date) is honored in place of the backoff when `respect_retry_after` is on, **capped at 120 s** so a hostile or mistaken header can't freeze a run (the *number* of waits is already bounded by `max_retries`; the cap bounds each wait's *duration*). A URL that exhausts its retries or fails permanently becomes a `FetchFailure` recorded in `RunResult.dead_letter` (URL + generic reason + attempt count) instead of crashing the run on the bare `raise_for_status()` it replaces; the run summary surfaces the dead-letter log and a transient-retry count (delivering the §2d run-observability "error counts"). A dead-lettered run is **not escalated** to a heavier tier — a classified fetch failure is a definite answer about the origin, not an empty page a browser might render differently, and re-fetching would only hit the same failing server (the same reasoning that already exempts a robots-`blocked` run). **Scope** of *this* slice is the sequential tier-1 httpx fetch path; **browser-tier navigation retry is a deliberate follow-on** that has since landed (see its decision note below), reusing this slice's classification and backoff. Two departures from the plan-as-written, recorded rather than hidden: (1) the retry loop is **hand-rolled, not `tenacity`** (§7 lists tenacity as a dependency) — the policy is ~30 lines of bounded loop + classification and needs to thread the injectable `sleep` seam the politeness gate already uses and to *return* a classified `FetchFailure` rather than raise-after-exhaust, both of which fit a small purpose-built loop more cleanly than tenacity's decorator/retry-state model; the §7 row is updated to reflect this. (2) The dead-letter URLs are surfaced on the summary like `blocked` URLs are; because a query string *can* embed a token, running both through the §2h redaction pipeline before shared output is a noted candidate for the redaction slice — not a weakening of the §2h non-negotiable, which governs *captured* secrets (HAR/storage), not the config's own request URLs.

**Decision — Phase-3.5 change detection (skip re-extracting unchanged pages).** The store lives in `spoor/operational/change_detection.py:ChangeDetector`, a per-domain, local-only JSON file (parallel to the tier-3 fingerprint cache) keyed by URL, remembering each successful fetch's `ETag`, `Last-Modified`, and a SHA-256 of the body. It is enabled by an opt-in top-level `change_detection: true` on the §2a config (a plain `bool`, not a sub-model — the mechanism needs no tuning knobs), and is **default off**: skipping extraction changes what a run produces (an unchanged page yields *no* records), which a one-shot scrape shouldn't get by surprise; a monitoring run turns it on. On a re-fetch the tier-1 path replays the remembered validators as a conditional `If-None-Match` / `If-Modified-Since` request; a **304 Not Modified** — or, when the server sends no validators at all, a body whose content hash matches — marks the page `unchanged` (recorded on `RunResult.unchanged`, surfaced on the summary), and its extraction is skipped. Four decisions worth recording: (1) **Store is the §0-sanctioned "runtime-learned" exception**, the same class as the fingerprint cache — a URL only ever appears as a runtime dict key, never a source literal, so `check_genericity.py` (which scans all of `spoor/`) stays clean; it is local-only (§2h) since a stored URL can embed a token. (2) **A first sighting always extracts** (nothing to compare), and a corrupt/malformed store loads empty rather than crashing — change detection degrades to "extract everything", never to a failed run. (3) **Pagination interaction is a natural consequence, not a hidden rule**: a 304 carries no body, so `_next_url` finds no next link and the crawl ends at the first unchanged page; a hash-matched 200 *does* still carry a body, so pagination continues past it. (4) **An unchanged run is not escalated** (`_should_escalate` now also excludes `unchanged`): zero records because the page matches a prior run is a definite "nothing changed" answer, not a selector miss a heavier tier would resolve — the same reasoning that already exempts `blocked` and `dead_letter`. **Scope** is the sequential tier-1 httpx fetch path; **browser-tier change detection is a deliberate follow-on** (a rendered navigation doesn't issue a conditional GET as cleanly), not covered here.

**Decision — Phase-3.5 browser-tier navigation retry (the retry note's follow-on lands).** The browser-tier navigation retry the retry slice named as a deliberate follow-on now lands, and it lands as **shared classification and backoff, not a second copy**. `spoor/operational/retry.py` was refactored so the HTTP-category classification (`_classify_status`), the `Retry-After` parsing (`_retry_after_seconds`, with the same 120 s cap), and the backoff (`_wait`) are transport-agnostic module functions; `RetryingFetcher` (tier-1 httpx) and the new `RetryingNavigator` (browser tier) are thin wrappers that differ only in *how* they attempt and *what* they catch. `Tier2Resolver._crawl` navigates through the navigator instead of a bare `page.goto(...)`: a transient navigation outcome — a 5xx/429 on the response, **or** a Playwright timeout / transport error (`PlaywrightTimeoutError` / `PlaywrightError`) raised by the navigation — is retried with backoff; a permanent 4xx or an exhausted transient one becomes the same `FetchFailure` recorded on `RunResult.dead_letter` and surfaced on the summary, and the browser tier's retries feed the same `retries` count. This replaces the previously-uncaught `page.goto` that would crash the whole run on the first navigation timeout. Three decisions worth recording. (1) **No Playwright import in `retry.py` (§0/layering).** The navigator takes the transient exception types from its caller (`transient_exceptions=(PlaywrightTimeoutError, PlaywrightError)`) and inspects only a small structural `_NavResponse` protocol (`status`, `header_value`) that Playwright's `Response` satisfies — so the operational retry module stays free of any browser dependency, and `navigate` is generic over the concrete response type so the caller keeps full access to its own `Response` (e.g. `.headers` for the §2c header signal). (2) **A dead-lettered navigation stops the crawl** exactly as a dead-lettered tier-1 fetch does — a page that never loaded has no next-link to follow — with `page.close()` still run via the existing `finally`; a `None` navigation response (a same-document navigation) is treated as a no-retry success with no status to classify. (3) **The transient-*exception* path is unit-tested, not BDD-tested**, because a live browser can't be made to raise a navigation timeout deterministically; the `.feature` drives a real browser against a scripted flaky loopback server for the HTTP-status paths (503-once-then-page, always-503, 404), and `RetryingNavigator`'s classification/backoff/exception handling is covered in `tests/test_retry_navigator.py`. Nothing here is site-specific (§0). This closes the browser-tier follow-on; **browser-tier change detection remains a separate deferred follow-on** (see the change-detection note).

**Decision — Phase-3.5 anti-bot / CAPTCHA detection (detection, never bypass).** The recognizer lives in `spoor/operational/challenge.py:detect_challenge`, a pure scan of already-fetched HTML that returns a `ChallengeSignal` (vendor + the matched marker) or None. Both resolution tiers run it on the page they fetched/rendered (`RunResult.challenge`), and the run summary surfaces it **loudly and high** ("CHALLENGE DETECTED (Cloudflare) — not scraped as data"), delivering §2d's "recognize known challenge-page fingerprints and fail loudly rather than silently returning a challenge page as if it were data." Three decisions worth recording: (1) **Markers are structural, not vendor hostnames** — widget CSS classes (`g-recaptcha`, `h-captcha`, `cf-turnstile`), challenge-token params (`__cf_chl`), interstitial title text ("just a moment...") — both to keep false positives low and so nothing reads as a hardcoded target domain. This matters because `scripts/check_genericity.py` scans *all* of `spoor/` (not just `core/`), so a literal `hcaptcha.com` in `operational/` would fail it; the tokens are vendor-generic anti-bot infrastructure recognition, the same §0-allowed class as parsing `robots.txt`, not knowledge of a target site. It is a maintainable, PR-extendable table. (2) **A challenge is recognized whether it rides a 2xx *or* sits behind an error status.** A challenge in an otherwise-successful (2xx) response is caught at extraction; a challenge served *with* an error status (a 403/503 Cloudflare interstitial) is *also* recognized, because such a fetch is both a dead-letter failure and a challenge and the operator deserves to see both. The tier-1 fetcher scans the *failing* response body and carries the recognized vendor on the `FetchFailure` as a new `challenge` field (the generic `ChallengeSignal` only, never the raw body — §2h); `Tier1Resolver` promotes it to `RunResult.challenge` when it dead-letters. The browser tier scans the rendered `page.content()` on a dead-lettered navigation (the DOM is the right source there; the navigator itself stays body-free). Detection is reset per attempt, so a terminal transport failure (a timeout with no body) after an earlier challenged attempt reports None rather than a stale hit. This closes the "challenge bodies behind an error status" follow-on the first anti-bot slice named; the two slices now cooperate rather than partition — the retry slice still labels the HTTP error, and this adds the "…and it was a wall" line beside it. (3) **Escalation is deliberately unchanged**: a challenged page that yields zero records still escalates to the browser tier — a passive JS check can clear on render, turning a tier-1 "challenge" into real tier-2 data — and only a challenge that survives to the final attempted tier is surfaced. Detection never attempts to *solve or bypass* a challenge; naming the wall is the whole feature.

## 2e. Exploration mode: mapping the full interaction space (post-v1 — see §4)

Everything so far assumes a config (§2a) tells the tool which fields/actions matter. This is a second, distinct mode: point it at a target with no config at all, and it autonomously discovers every actionable element, interacts with each one, captures the full signal bundle (§2c/§2d) before and after, and builds a graph of `state --action--> state`. The end product is a generated wiki — one page per state, one page per transition, browsable — that answers "what happens, on every signal level, when I press this button" for the entire product, not just the fields a user thought to ask about.

**Prior art worth building on, not depending on directly.** Crawljax (now maintained under the OWASP ZAP project, `zaproxy/crawljax`) solved the core research problem here years ago: systematically firing every user-triggerable event on an AJAX-heavy app and building a state-flow graph. It's Selenium-based, not Playwright, so the right move is porting its *algorithm* onto our existing Playwright base rather than adding it as a dependency — specifically its **state abstraction function**: normalize the DOM (strip timestamps, session IDs, counters, anything volatile) and hash it, so revisiting an equivalent state is recognized as such instead of exploding into infinite near-duplicates. Actionable-element discovery reuses the accessibility tree signal already planned in §2c (it already labels roles like button/link/textbox generically, no new mechanism needed).

**Destructive-action safety (per your decision): sandbox-only, non-configurable.** The engine maintains a registry of declared local/self-hosted targets (matches on `localhost`/`127.0.0.1`, or a target explicitly marked `sandbox: true`). Only against a registry match will it interact with actions a heuristic flags as destructive/irreversible (keyword/ARIA matching on delete, remove, buy, purchase, pay, confirm, send, submit-payment, log out — a maintainable, PR-extendable list, not a fixed set). Against anything else — any real external site — those actions are always skipped and logged as skipped; there is deliberately no flag or config option that relaxes this for a non-sandbox target. This is a hard boundary, stated plainly in the README, not a tunable default: the worst case for exploring a real, unvetted site is "missed a state," never "placed a real order" or "deleted real data."

**Run-level controls are core, not optional hardening.** Every exploration run has a hard, user-set budget — max states discovered, max wall-clock time, max requests — that auto-stops the run when hit, plus a manual kill switch to stop a running exploration on command. Both ship in the same phase as the rest of §2e's safety system (Phase 5), never as a follow-up: a run that can't be bounded or stopped is itself a reliability/safety gap under §1's stance and the "core architecture, not later hardening" principle, not a nice-to-have.

This registry is currently **self-declared** (a config sets `sandbox: true`), which is a known, accepted gap for the PoC, not something to solve now — see §9. The current guardrails plus running only against the dedicated test fixtures (§5) is the deliberately-chosen "safe enough for a PoC" posture; hardening the registry itself (e.g. restricting it to `localhost`/private IP ranges regardless of what a config claims) is real future work, tracked rather than blocking anything today.

**Signal capture during exploration reuses the existing cost tiers — and is request-driven, not judgment-driven.** Default to the free/near-free signals from §2c/§2d for every single transition (screenshot, accessibility snapshot, storage-state diff, HAR delta, console diff) — that's the bulk of the wiki's content. The expensive ones (full video, heap snapshots) are reserved for states matching an explicit rule the user configures (e.g. "always deep-capture states matching `/checkout/*`," or "deep-capture anything under this DOM subtree") — corrected from an earlier draft of this section, which described the system autonomously deciding a state looked "interesting." Per §1, Spoor doesn't make that judgment call itself: it records what it's told to, at the depth it's told to, nothing more.

**Wiki generation is comparatively cheap.** The graph (nodes = states with their captured signal bundle, edges = actions with their before/after diff) is just structured output; rendering it as a browsable site means reusing an existing static site generator (MkDocs or Docusaurus) for navigation/search, with a small templating layer turning each node/edge into a page, plus an embedded graph visualization (Mermaid works for smaller graphs; `vis.js`/`pyvis` for larger ones) for the overview. No custom wiki engine to build. *(Superseded in the build: the slice-6a decision note below chose a self-contained Jinja2 renderer over reusing MkDocs/Docusaurus, keeping Mermaid for the overview — see that note for the rationale.)*

**This is the real test of §0's no-tailoring rule.** The four archetype fixtures (§5) stop being just tier-cascade validation and become the proof that the *exploration algorithm* itself is generic: if it can autonomously map Juice Shop's vulnerability-laced flows, Sauce Demo's checkout, a self-hosted ERP's CRUD-heavy forms, and a Netflix-clone's media/auth state — with the same unmodified state-abstraction and safety logic — that's the real evidence this isn't tailored to any one of them.

**Honest scope note.** This is a substantial second project riding on top of the v1 stack, not a small addition — realistically another **6–9 weeks** (state-abstraction tuning, the safety system with its own dedicated test coverage, graph storage, and wiki templating each take real iteration), most likely landing as v2 rather than folded into the v1 estimate in §4. It's written up in full here because the design is worth locking in now, even though building it comes after v1 ships.

**Decomposition (agreed) — §2e in shippable, gated slices.** Rather than one large drop, exploration mode is built in order: (1) **safety gate** — sandbox registry + destructive-action classifier + the always-skip-non-sandbox rule; (2) **state-abstraction function** — DOM normalize + hash; (3) **actionable-element discovery** — reusing the §2c accessibility tree; (4) **run-level controls** — budget + kill switch (ship *with* the safety system, per above, not after); (5) the **explorer loop** tying 1–4 into a `state --action--> state` graph; (6) **wiki generation**. Each is its own BDD-first PR.

**Decision — §2e first slice (safety gate), shipped.** Exploration begins with its safety foundation, built before anything that can fire an action exists — the non-negotiable, and the smallest self-contained, browser-free, in-process-testable piece (mirroring how §2f started with its thinnest testable slice). Two pure-logic pieces plus the gate combining them: `spoor/security/sandbox.py:is_sandbox(target, *, declared)` recognizes a sandbox only by loopback host (`localhost`/`127.*`/`::1`) or an explicit declaration; `spoor/exploration/safety.py` holds the PR-extendable `DESTRUCTIVE_KEYWORDS` set (the §2e list: delete, remove, buy, purchase, pay, confirm, send, submit-payment, log out), an `is_destructive(label, role)` whole-word matcher, and `evaluate_action(...)` returning a `GateDecision(allowed, reason)`. A non-destructive action is allowed anywhere; a destructive one only inside a sandbox, else skipped with a log-ready reason. **The non-negotiable is enforced structurally, not by discipline:** `evaluate_action`'s signature is exactly `(target, label, role, declared_sandbox)` — no bypass/force/override parameter exists — and `exploration_safety.feature` pins this with a scenario asserting that parameter set, alongside behavioral scenarios (destructive-on-real-target → skipped; destructive-in-sandbox → allowed; non-destructive → allowed anywhere). Emitting the skipped-log line and actually driving actions belong to the explorer loop (slice 5); this slice only *decides*. The registry stays self-declared (§9 gap, accepted).

**Decision — §2e second slice (state abstraction), shipped.** The Crawljax state-abstraction function, still pure logic: `spoor/exploration/state.py:state_id(html)` normalizes a page's DOM and returns a stable SHA-256 hex digest, so revisiting an equivalent screen is one state, not an infinite spray of near-duplicates. Identity is built from (a) the tag **structure** in document order/nesting, dropping `script`/`style`/`noscript`/comments; (b) a small allowlist of stable, **state-bearing attributes** (`role`, `type`, and the flags `disabled`/`checked`/`selected`/`open` + ARIA equivalents) — every other attribute value (`id`/`class`/`href`/`value`/`nonce`/`data-*`) is ignored so a session token or random React id can't fork a state; and (c) **visible text with volatile spans masked** (timestamps, clock times, UUID/long-token strings, and digit runs → a constant placeholder), so a cart badge of 3 vs. 4 is one state while a "Maintenance" vs. "Orders" heading is two. Parses via `parsel` (already the core extraction parser — no new dependency). `exploration_state.feature` pins both directions (volatile-only edits collapse to one id; genuine structure/text/state-attribute differences separate) and determinism. **First, PR-tunable cut** — §2e's own note that state-abstraction tuning takes real iteration; the known trade-off is that two screens differing *only* by a meaningful number collapse (accepted, it's the abstraction's point), and attributes outside the allowlist don't distinguish states yet. Generic to every target (§0).

**Decision — §2e third slice (actionable-element discovery), shipped.** Still pure logic, and reusing an existing mechanism rather than inventing one: the §2c accessibility-tree signal (`Accessibility.getFullAXTree`, as `AccessibilityCollector` captures it) already labels every node with a generic ARIA role, so "what can the explorer act on here?" is filtering that node list. `spoor/exploration/discovery.py:discover_actions(ax_nodes)` keeps the nodes whose role is in the PR-extendable interactive set `ACTIONABLE_ROLES` (button/link/textbox/checkbox/radio/combobox/menuitem/tab/switch/…) and that aren't `ignored`, returning an `ActionableElement(role, name, backend_node_id)` per surviving node. The accessible **name** is precisely the label the safety gate (slice 1) classifies; the **backend node id** is the CDP handle the explorer loop (slice 5) will use to locate the element to act on it. Document order and every interactive occurrence are preserved — deduplication is the graph's job, not this slice's — and the reader is tolerant of missing fields (no name → empty label; no backend id → `None`), so an icon-only button is still a candidate. `exploration_discovery.feature` pins that only interactive, non-ignored roles survive, that name and DOM handle are preserved, that an unnamed element is still discovered, and that a page with no interactive roles yields nothing. This slice only *discovers*; driving actions is the explorer loop. Generic to every target (§0): the same role set for all.

**Decision — §2e fourth slice (run-level controls), shipped.** The budget + kill switch the "run-level controls are core, not optional hardening" note above requires, landed *with* the safety system rather than after — still pure logic. `spoor/exploration/control.py` holds two pieces: `RunBudget(max_states, max_requests, max_seconds)` — the user's hard bounds, each optional (`None` = that dimension unbounded), each set bound validated positive (a zero/negative bound is a config error, not a silent instant stop); and `RunController`, which tracks one run's consumption (`record_state`/`record_request`), reads wall-clock through an **injectable `clock`** (default `time.monotonic`; deterministic in tests, the same seam the retry module uses for sleep), and holds a **thread-safe kill switch** (`kill()` sets a `threading.Event`, so a stop-on-command can arrive from another thread). `check()` returns a `StopDecision(should_stop, reason)` with a log-ready reason; **the kill switch is checked before the budget**, so a manual stop is always reported as such, and budget dimensions are then checked in order (states, requests, time). The explorer loop (slice 5) records progress and calls `check()` before each step; this slice only *decides*. `exploration_control.feature` pins each bound stopping the run at its threshold (and not before), a within-bounds run continuing, positive-bound validation, and — pinning the §2e non-negotiable that a run is always stoppable — that the kill switch stops even an unbounded run and takes precedence over a reached budget bound. Generic to every target (§0).

**Decision — §2e fifth slice, sub-slice 5a (explorer loop, orchestrator), shipped.** The pure-logic core of the explorer, no live browser yet. `spoor/exploration/graph.py` holds the `ExplorationGraph` — nodes are abstract states keyed by the slice-2 `state_id` (each carrying the actions discovered there), edges are fired actions (`from --action--> to`), and gate-refused actions are recorded separately as skips, so the map honestly shows both what was explored and what was left alone; states dedupe by id (adding a known state is a no-op). `spoor/exploration/explorer.py:explore(driver, *, target, controller, declared_sandbox=False)` ties the four earlier slices together: it discovers each state's actions (slice 3), asks `evaluate_action` which may be fired (slice 1), recognises a revisited state by `state_id` so the walk is finite (slice 2), and calls `controller.check()` before every action so a budget or the kill switch always stops it (slice 4). The walk is **depth-first with reset-and-replay** navigation — to revisit a state it resets the driver and replays the path that first reached it, so it assumes no back button and works for any deterministic driver — and only recurses into a genuinely new state (a transition back to a known state is recorded but not re-explored). The browser sits behind a `BrowserDriver` `Protocol` (`reset`/`state_html`/`ax_nodes`/`perform`), so the whole loop runs in-process against a fake app; `exploration_loop.feature` pins mapping a two-state app, collapsing a revisited state to one node, the §2e non-negotiable both ways (a destructive action is skipped and its state never reached on a real target, but fired inside a sandbox), and stopping on a state budget or a pre-thrown kill switch. The real Playwright `BrowserDriver`, a live-browser run, and the `spoor explore` command are sub-slice 5b; per-transition signal capture is 5c. Generic to every target (§0).

**Decision — §2e fifth slice, sub-slice 5b (real driver + `spoor explore` command), shipped.** The orchestrator from 5a, now driving a real headless browser end to end. `spoor/exploration/driver.py:PlaywrightDriver` satisfies the `BrowserDriver` protocol against a headless Chromium page: it mirrors the tier-2 Playwright lifecycle (`spoor/core/extract.py`) but keeps **one page open for the whole run** (the explorer needs a persistent live page to drive), reads the accessibility tree over CDP (`Accessibility.getFullAXTree`, the same call the §2c a11y signal uses) for discovery, and returns `page.content()` as the state HTML. The one genuinely new piece is `perform`: reset-and-replay reloads the page, and a reload reassigns every DOM/accessibility node id, so the discovered `backend_node_id` is only meaningful inside the snapshot it came from and **cannot** be used to click after a replay — so `perform` re-locates the element in the *current* page by its accessibility **role and name** via Playwright's role locator (which also gives auto-waiting and actionability for free), acting on the first match in document order (deterministic; a known first-cut limitation for role+name collisions). Teardown is context-manager-guarded (page → context → browser → Playwright, each swallowing a close error). `spoor explore <url>` is the first runnable exploration command: it builds a `RunBudget` from `--max-states`/`--max-requests`/`--max-seconds` (a non-positive bound is a `BadParameter`, not a silent stop), installs a SIGINT handler that throws the kill switch (so **Ctrl-C stops gracefully at the next action**, not mid-click) and restores the prior handler in a `finally`, runs the driver, and prints a plain-language summary (states discovered / transitions / actions skipped, with a note when skips happened on a non-sandbox target). `--sandbox` is the only way to exercise destructive actions and its help states it is local/test-systems-only — the §2e non-negotiable holds unchanged (no bypass flag; the gate still decides). `exploration_browser.feature` drives real Chromium against a two-page loopback fixture (Home ⇄ Next) and asserts the summary reports two states, two transitions, zero skips — the one exploration scenario with a live socket and a real browser launch, since a browser can't use the in-process fake transport. The plain-language sandbox rule is stated in the README with this command (per the decomposition note's "state the sandbox rule plainly in README" requirement). Per-transition signal capture is sub-slice 5c. Generic to every target (§0).

**Decomposition (agreed) — §2e sub-slice 5c (per-transition signal capture) in two, logic-first.** 5c captures §2e's "free/near-free" signal bundle for every transition — screenshot, accessibility snapshot, storage-state diff, HAR delta, console diff — which is more than one cleanly-reviewable PR because some signals (a11y count, DOM, storage) are cheap reads already near the driver while others (screenshot hash, HAR delta, console events) need live-browser plumbing. **Decision — §2e sub-slice 5c-i (signal model) then 5c-ii (live capture), shipped.** 5c-i landed the pure model: `spoor/exploration/capture.py` holds `StateSignals` (a state's free-signal bundle — accessibility node count, console messages, storage keys, network requests, screenshot hash) and `diff_signals(before, after) -> TransitionSignals` (what console/storage/network entries appeared, what storage was removed, the signed a11y-node delta, whether the screenshot changed; additions keep first-seen order and dedupe). The graph now carries a bundle on each `StateNode` and a diff on each `Transition` (both optional, default `None`), and `explore` captures the bundle either side of every fired action through a new `capture_signals()` seam on the `BrowserDriver` protocol — exercised in-process against the fake driver. 5c-ii then filled that seam on the real driver: `PlaywrightDriver.capture_signals()` reads all five signals from the live page — the CDP a11y node count, the console and network-request buffers accumulated by page listeners attached at launch (so a transition's diff is the slice between its before/after snapshots, correct under reset-and-replay), the current `localStorage`+`sessionStorage` keys, and a **perceptual (dHash) hash of a screenshot reusing the tier-3 visual hasher** (`spoor/core/visual.py`) — chosen over a byte hash so a transition is flagged as changing the screenshot only on a real visual change, not on anti-aliasing/cursor noise. Every signal is opportunistic (a read that fails is recorded empty, never failing the run — the §2c collector stance). `exploration_signals.feature` (5c-i) pins the diff model in-process; `exploration_signals_live.feature` (5c-ii) drives the real driver against a signal-rich loopback fixture and asserts genuine console/storage/network/a11y/screenshot capture and a real click's diff. **Decision — §2e sub-slice 6a (pure wiki renderer), shipped.** Two scoping decisions were taken with the maintainer before building (recorded here because both depart from an earlier draft of the §2e "wiki generation is cheap" note). (1) **Self-contained renderer, not a reused static-site generator.** The note above suggested reusing MkDocs/Docusaurus with a small templating layer; instead 6a ships a **self-contained Jinja2 renderer** producing plain static HTML directly, with the graph overview drawn by **Mermaid**. Rationale: MkDocs/Docusaurus each pull a heavy toolchain (a full site generator, for MkDocs a Python dep tree, for Docusaurus a Node build) to render what is a fixed, small page set; a direct Jinja2 template layer is fewer moving parts, no build step, and keeps the output honestly local-first. `jinja2` is added to the core dependencies (its first use in the project); Mermaid is loaded from a CDN by the index page (the pages themselves are static and readable offline — only the overview *diagram* needs the network to draw, an accepted first-cut limitation). (2) **Hash-only screenshots for now.** The captured screenshot signal is a perceptual hash (5c-ii), not stored image bytes; 6a therefore reports per transition whether the screenshot *changed* and shows the per-state hash, but embeds **no images** — capturing and embedding the actual screenshots is a deliberate follow-on. **§2h redaction is mandatory and structural here:** the wiki is a shared-output surface, so every captured value it renders — console messages, storage keys, network URLs, action labels — is passed through `spoor/security/redaction.py:redact` before rendering, and Jinja2 autoescaping (on for every template) independently neutralizes HTML/script injection from a captured value; `exploration_wiki.feature` pins that a bearer/vendor token logged to the console never appears raw in any page. The renderer is a pure `build_pages(graph, *, target) -> dict[str, str]` (filename → HTML, testable with no disk) plus a thin `render_wiki(graph, out_dir, *, target)` that writes them; state/transition page filenames are stable indices into the graph's insertion order. Nothing here is site-specific (§0): the same templates render every target's graph. The CLI `--wiki` flag and the live-archetype reliability test are sub-slice 6b. One §0-mechanism refinement rode along: `scripts/check_genericity.py` scans *all* of `spoor/`, so the wiki's literal Mermaid CDN host tripped it; rather than obfuscate the URL, the checker gained a small, explicit `ALLOWED_ASSET_HOSTS` allowlist (`cdn.jsdelivr.net`) for third-party **static assets Spoor's own output loads** — the same "generic infrastructure, not a *target* site" category as the existing `localhost`/loopback allowance, extended deliberately one entry at a time (never a wildcard). This does **not** weaken the §0 non-negotiable, which forbids baking in knowledge of a *target*; a CDN Spoor fetches a library from is not a target. The maintainer chose this over vendoring Mermaid's ~2.8 MB minified blob into the repo (heavier, hand-updated) or embedding un-rendered Mermaid source (no in-browser diagram).

**Decision — §2e sub-slice 6b (`--wiki` CLI wiring + live-archetype reliability + graceful degradation), shipped.** The 6a renderer, now reachable from the command line and proven against real sites. (1) **CLI wiring.** `spoor explore <url> --wiki <dir>` renders the mapped graph to a browsable site after the crawl (via `render_wiki`) and echoes the written `index.html` path; the flag's help is plain-language (no §-refs). `exploration_browser.feature` gained a second live-Chromium scenario that reruns the Home⇄Next crawl with `--wiki` and asserts the command reports where the wiki was written and produces a complete site (index + a page per state and per transition) whose overview counts match the run. (2) **Live-archetype reliability test.** Per the maintainer's "check the wikis are reliably created every time" direction, `tests/test_integration_wiki.py` (marked `integration`, skips when the bench is down) crawls **both** archetypes — Juice Shop and Sauce Demo — under a small budget (`max_states=4, max_requests=8, max_seconds=120`), renders the wiki to a durable `test-output/` dir, and asserts a **structural-completeness contract** rather than golden counts (a live SPA's exact graph isn't a contract): exactly one page per state and per transition plus the index, every page well-formed HTML, the index's counts matching the graph, and every state/transition link resolving to a written file. It ran green twice against both sites. (3) **Graceful degradation — a real defect the reliability test surfaced.** The first live run *crashed*: `PlaywrightDriver.perform` let a click that couldn't land (Juice Shop's `Open Sidenav` under a modal overlay — a `Locator.click` timeout) propagate and abort the whole exploration, so **no** wiki was produced. On a live, dynamic target a discovered element being un-actuatable by reset-and-replay time (gone, hidden, covered) is *expected*, not exceptional. The fix keeps the explorer browser-agnostic: a new domain exception `spoor/exploration/explorer.py:ActionError` is part of the `BrowserDriver.perform` contract; `PlaywrightDriver.perform` catches `PlaywrightError` (which includes the click timeout) around the click and re-raises it as `ActionError` (terse, run-varying timeout value omitted for stable text; the Playwright detail preserved as the chained cause); and the `explore` loop catches `ActionError` around navigate+perform, records the action as a skip (`could not be performed: …`) and continues — the next iteration resets and replays afresh, so one dead element never aborts the map. `exploration_loop.feature` pins this in-process (a fake driver whose `perform` raises `ActionError`: the action is skipped and the rest of the map still built), and `tests/test_exploration_driver.py` pins the driver's timeout/detached → `ActionError` translation and the swallowed post-click load-state timeout without needing a browser. With the fix, Juice Shop yields a (degenerate but valid) 1-state wiki and Sauce Demo a rich multi-state/multi-transition one, both produced reliably. Making a *dynamic SPA's* home actions actually actuate (dismissing splash/cookie overlays before discovery so the graph is richer) is a separate exploration-productivity concern, backlogged (§9), not part of this slice. Generic to every target (§0).

**Decision — §2e sub-slice 6c (state-page readability), shipped.** A fresh wiki generated from the live PrestaShop crawl (after 7e) rendered, linked, and redacted correctly but read poorly, and the slice fixes the two concrete defects found — both generic (§0), neither touching the graph model or the safety gate. (1) **Human-readable state labels.** States were labelled only by their opaque 64-char `state_id` (shortened to 12 chars for display), so the index lists and the Mermaid overview were a wall of near-identical hashes. `StateSignals` gained a defaulted `title: str = ""` that `PlaywrightDriver.capture_signals` fills from the page's `document.title` (opportunistic like every other signal — a torn-down context or a titleless page yields `""`); the renderer's `_state_label(sid, signals)` uses the **redacted** title as the state's label on its own page, in the index state/transition lists, and in the graph nodes, falling back to the short id when there is no title, so every state stays identifiable. The full hash is still shown as the state id on its page. Generic to every target (§0): the same label rule and collapse render every target's graph.

**Decision — §2e sub-slice 6d (network categorization + per-visit signal scoping), shipped.** Two follow-on refinements to the same "state pages read poorly" thread as 6c, both maintainer-requested after reviewing a live wiki, both generic (§0) and neither touching the graph model or the safety gate. (1) **Network requests grouped by kind.** A state page showed one flat list of every request URL; 6d collates them under a small fixed taxonomy — Documents, Scripts, Styles, Images, Fonts, Media, Data, Other — with a per-group count, so a reader sees at a glance what the page loaded. The kind is a **URL-only heuristic** (`spoor/exploration/wiki.py:_request_category`): the file extension of the last path segment maps through a fixed table, an extensionless path is a Document unless it names an `/api/` (→ Data), and an unrecognised extension is Other. This is deliberate — Spoor captures request URLs, not response content-types, so the label is best-effort, not a guarantee; but it needs no new capture and stays generic across every target. A timeline view was considered and **not** built: an ordered timeline needs per-request capture-layer timestamps the signal bundle does not carry, so categorization (which the captured URLs already support) shipped instead. (2) **Per-visit signal scoping (supersedes 6c's "whole-run buffer" framing).** 6c collapsed repeated console/network lines but left the underlying defect: the driver's console and network buffers accumulated for the *whole run*, so a state reached late still carried every earlier walk's output (collapse only hid the duplication). `PlaywrightDriver.reset` now **clears both buffers**, so each reset begins a fresh visit and a state's recorded console/network reflects only the walk that reached it — not the session's cumulative output. This is safe for transition diffs: `diff_signals` is computed from a before/after pair straddling a single `perform` with **no reset between them** (confirmed against `explorer.walk`), so clearing at the earlier reset changes only the absolute per-state contents, never a transition's delta. Collapse (6c) still earns its place — a chatty library or polled endpoint repeats within a single visit's reloads. `features/exploration_signals_live.feature` gained a scenario proving a capture after a reset drops a prior click's `/ping.txt` request and `going next` console line while still showing the fresh load's `home ready`; `tests/test_exploration_driver.py` pins the buffer-clear browser-free. `features/exploration_wiki.feature` gained the network-grouping scenario. Generic to every target (§0): the same taxonomy and the same reset scope every target's signals.

**Decomposition (agreed) — §2e slice 8 (visual capture): embed screenshots in the wiki, opt-in and staged.** The maintainer asked to finally surface the *pixels* the wiki has only ever hinted at (the hash and the honest "none" screen-capture column of 6e), the §9 "Visual capture" backlog item. **Decision — §2e sub-slice 8f (stream each screenshot to disk as it is captured; hold only a reference), shipped.** A memory fix the maintainer required before comprehensive screenshotted crawls were possible: the 8b/8d/8e sinks held every captured image's **bytes** in memory until `render_wiki` wrote them all out at the end, so a deep run with `--screenshots` accumulated the whole run's pixels in RAM and OOM-killed a comprehensive crawl. 8f inverts the ownership: each capture is **written to disk the instant it is taken**, and the sinks hold only the subfolder-relative **filename reference**, never the bytes. `explore` gained a required `screenshot_dir: Path` (validated non-None whenever either screenshot sink is passed, and in the CLI set to the `--wiki` directory so images and the pages that embed them land together); a new `_stream_capture(data, screenshot_dir, name)` helper writes one capture under `screenshots/<name>` as it is produced (creating the subfolder on first write) and returns the stored name, or None for a capture the driver couldn't take — so the sink stays honest about a missing image. The capture-time state index is `len(graph.states) - 1` — the new state's insertion position, which equals the renderer's `state-{index}` enumeration (`graph.states` returns the states in insertion order), so the streamed filename and the embedded `<img src>` always agree. **Decision — §2e sub-slice 8g (deduplicate screenshots and store a clip as a crop of its page), shipped.** The waste 8f's streaming exposed next: a comprehensive live crawl wrote the **same picture** to disk many times — one run produced 2,409 element clips against just 40 full-page shots, nearly every clip a region of the page it came from, and states that render identically each wrote their own copy. 8g removes both redundancies so the wiki refers to one shared picture. **Two mechanisms, both deterministic and generic (§0 — pure image maths, nothing site-specific).** *(1) Duplicate detection.* A new `ScreenshotStore` (one per run, over the screenshot dir) routes every capture through `add(data, preferred_name) -> ImageRef`: a **byte-exact** duplicate (SHA-256 `content_key`) reuses the existing file; a **near-identical** capture (the same screen re-rendered with only anti-aliasing/cursor noise) is matched by the tier-3 dHash `perceptual_hash` within a tight **3-bit** Hamming distance (`_NEAR_DUPLICATE_BITS`) and reuses it too; otherwise the bytes are written and remembered. A **flat** image (dHash 0) is matched byte-exactly *only*, never perceptually, so distinct blank screens are never collapsed together. This never merges two **states** — only the image a state's page embeds is shared; the state pages stay separate (the graph identity is still the DOM `state_id`). *(2) Sub-image containment.* A clip that is a region of its state's full-page shot is stored as a **crop reference** into that picture — no file of its own. The element's on-page geometry is used first: a new opt-in `_ElementBoxCapable` protocol exposes `element_box(action) -> (x,y,w,h)|None` (the live `PlaywrightDriver` reuses its `DOM.getBoxModel` border-box path), and `_contained_box` **verifies** the hint by comparing the container region at that origin, sized to the clip's *own* decoded dimensions, pixel-for-pixel (robust to sub-pixel rounding); when the hint is absent or fails, the clip is located by exact pixel search (`find_subimage`, topmost-leftmost, candidate-bounded). Only a clip in no bigger picture is written (deduped) as its own file. **Type shape (supersedes 8f):** the bare `str` filename references become a frozen `ImageRef(src, box)` — `src` the subfolder-relative filename, `box` an optional `(x,y,w,h)` crop of it, `None` meaning the whole file; sinks are now `MutableMapping[str, ImageRef]` and `ElementShot.clip`/`.opened` are `ImageRef | None`. 8f's `_stream_capture` helper is replaced by the store's `add`. New pure module `spoor/exploration/dedup.py` holds the deterministic primitives (`content_key`, `decode`→`UndecodableImage`, `find_subimage`); `screenshot_store.py` holds the stateful writer; the explorer decodes the container once per state and resolves each clip via `_resolve_clip`/`_contained_box`. The wiki renders a crop reference as a CSS-cropped `<span class="screenshot-crop" … background-image:url('…') background-position:-x -y>` (a whole-file ref stays an `<img>`), via a shared `_image_view`/`shot` macro. **§2h posture unchanged:** dedup and containment only ever touch pixels a caller already opted into capturing, an `ImageRef` carries nothing but a filename and integers, and a default run still writes no images. Built BDD-first — `exploration_screenshot_dedup.feature` pins seven scenarios (identical screens share one file; near-identical share one file perceptually; clearly-different stay separate; a contained clip via geometry and via pixel search each become a crop reference with no own file; an uncontained clip gets its own file; a re-run writes the identical file set) with **real-PNG Pillow fakes** so decode/hash/search run for real; the fast, browser, and integration tiers stay green, and the live integration assertion was corrected to embed each state's *own* reference (dedup may point a later state at an earlier state's file) rather than assuming `state-{index}.png`. Generic to every target (§0): the same dedup-and-crop path runs for every site.

**Decomposition (agreed) — §2e slice 9 (breadth-first traversal + depth budget + URL-path frontier): peel the site like an onion.** The maintainer observed that shallow, high-value pages — a shop's top-level categories (`/4-men`, `/9-art`), brand pages, the cart view — were missing from real maps, while deep product/variant tendrils were mapped. A throwaway diagnostic against a live PrestaShop bench (127.0.0.1:8080, not committed) corrected the assumed cause and grounded this slice: **(a)** the home page exposes **89 `link` nodes / 35 distinct first-layer paths** — every "missing" page (`/4-men`, `/9-art`, `/7-stationery`, `/brand/…`, `/cart?action=show`) is one click from home and *is* discovered as a gate-permitted `link`; **(b)** all six probed pages, including `/7-stationery` vs. its `?q=Availability-In+stock` filter, produced **six distinct `state_id`s** — so state-abstraction collapse is *not* why they were missed. Confirmed: it is ordering + budget, not discovery and not collapse. Three agreed changes, one slice: **(1) Breadth-first traversal** — replace the recursive DFS walk with a FIFO frontier of `(state_id, path)` so the crawl peels layer 0 (home) fully, then everything one click away, then layer 2, maximizing coverage of shallow structural pages for any budget. Reset-and-replay, verification (7d), and layer recovery (7c) are unchanged — only the order states are dequeued for expansion changes. **(2) `--max-depth` budget** — a first-class "don't go past the Nth layer" knob (added to `RunBudget`, validated positive): a state at depth *d* is *expanded* (its actions fired) only when *d* < `max_depth`, so reached/screenshotted states go up to depth `max_depth` but the crawl doesn't descend further; unbounded when unset. Unlike the states/requests/seconds bounds (which *stop* the run via `controller.check()`), `max_depth` *prunes* the frontier and never stops the run — documented as such. **(3) URL path forks the frontier** — the frontier's already-expanded key becomes `(state_id, url_path)` where `url_path` is the URL **path only** (query and fragment dropped), read from a new `BrowserDriver.current_url()` (trivially `page.url` on the live driver; the diagnostic confirmed it is available and correct after navigation, but it was previously unexposed and uncaptured). **Graph identity stays the DOM `state_id`** (the maintainer's explicit choice): one node and one screenshot per DOM hash, so near-duplicate pages never multiply in the wiki. Honest scope: the diagnostic showed real catalog pages already differ by DOM, so this fork is a **narrow safety net** for the "different URL, identical DOM" case (e.g. two empty listing pages), included now at the maintainer's direction rather than because those named pages needed it. Non-negotiables untouched: the safety gate still decides every fire (§2e), reset-and-replay stays verified (7d), and the mechanism is generic to every target (§0). Built BDD-first; in-process fake-driver scenarios pin BFS order (a budget that reaches shallow siblings under BFS where DFS would reach a deep descendant), the depth bound (expansion stops at `max_depth`, deeper states unreached), and the URL fork (a distinct path with an identical DOM is still expanded; a query-only variant is not).

**Decision — §2e slice 9b (destination-hint prioritisation: peel the onion in priority order), shipped.** Folded onto the slice-9 `explore-breadth-first` branch at the maintainer's direction, after the observation that a front-page link carries a real destination in its `href` (`ART` → `/9-art`) — a free signal already on the page. Slice 9 made the walk breadth-first, so the *layers* are peeled in order; but within a layer the actions still fired in discovery (document) order, so under a tight budget a deep-linking element discovered first (`/x/y/z`) could consume the budget before a shallow, top-level sibling (`/a`). 9b orders each state's actions by their **destination depth** — the number of non-empty path segments in the link's target URL — shallowest first, so structural, high-value pages are tried before deep tendrils *within* each BFS layer too. Three deliberate bounds keep it safe and generic: **(1)** the destination is a **hint, not a contract** — `ActionableElement.destination: str | None` (defaulted `None`, so every existing construction is unaffected); a button, a JS control, or an unresolved target has no destination and sorts **after** every known one (`_NO_DESTINATION_DEPTH`), falling back to plain discovery order via a **stable** sort, so nothing that used to be tried stops being tried. **(2)** It changes **reach order only** — the graph's stored action order is untouched, so the 8d/8e per-element and opened-contents screenshot alignment (indexed by discovery position) is preserved exactly. **(3)** It is site-agnostic (§0): depth is counted from the URL path structure, no host or path string is special-cased. The live driver reads the hint generically — `ax_nodes()` now issues one extra `DOM.getDocument` (pierced) to build a backend-node-id → `href` map, resolves each anchor's href against the live `page.url`, and reduces it to a URL path; empty hrefs, in-page fragments (`#…`), and non-navigational schemes (`javascript:`/`mailto:`/`tel:`) carry no destination. **Decomposition (agreed) — §2e slice 7 (exploration robustness): settle first, then recover.** Slice 6b closed by backlogging "make a dynamic SPA's home actions actually actuate (dismiss splash/cookie overlays before discovery)" as an exploration-productivity concern. Before building it, a live diagnostic against the §5.1 Juice Shop bench (throwaway, not committed) corrected the assumption behind that note. The dominant reason Juice Shop skips on `spoor explore` is **not** an overlay intercepting the click: the failing control (`Close Welcome Banner`) was present, visible, uncovered, and not inert every time it was inspected, and it clicked fine with the existing `get_by_role(name, exact=True)` locator *once the page had settled*. The real causes are (a) **unsettled, nondeterministic state** — discovered-element counts varied 4 → 6 → 7 → 22 across identical runs, because the Angular app renders the welcome dialog, the cookie bar, and a "language changed" snackbar asynchronously *after* `networkidle`, and some auto-dismiss — and (b) the resulting **relocation race**: reset-and-replay reads and acts against a half-rendered DOM, so an element found in one snapshot may be absent or not-yet-actionable by click time. This directly breaks the reset-and-replay determinism the whole explorer rests on. Genuine modal interception (a `cdk-overlay-backdrop` making underlying elements unclickable) is a real but *smaller and rarer* category — under a modal the background is usually `aria-hidden`/inert, so those elements are not even discovered.

So slice 7 is built in three BDD-first sub-slices, in order, each generic to every target (§0) and none weakening a non-negotiable — Juice Shop is only the *witness* that the generic mechanism works, never a special case in the code.

**7a — robust actuation (the deepest fix).** The `Close Welcome Banner` skip was a *relocation* failure, not timing: discovery reads the element from the **CDP accessibility tree**, but `perform` re-finds it through Playwright's *separate* ARIA name engine, and the two compute the accessible name differently, so `get_by_role(name, exact=True)` matched nothing on an element that was visible and uncovered. The fix keeps one engine end to end: at act time, re-read the **live CDP tree** (the same source discovery used, so names are consistent by construction), find the target node, scroll it into view, and actuate by **coordinates with a real mouse click** — trusted CDP `Input` events, which work identically headless and headed. Coordinates are never stored or guessed: the viewport is pinned (fixed size, device-scale-factor 1, so layout is reproducible), the box centre is read *live* from the current element, and `elementFromPoint(centre)` **verifies** the point resolves to the target before any click. If it resolves to something else, that is a precise, generic signal the element is genuinely covered (→ 7c) or mislocated (→ flagged) — a coordinate is computed, confirmed against the DOM, then used, never trusted blind.

*Shipped.* `spoor/exploration/actuation.py` holds the pure verdict (`classify` → ACTUATE / COVERED / NOT LOCATED) and the shared relocator (`find_target`, which runs `discover_actions` itself so act-time and discovery-time matching cannot diverge); `PlaywrightDriver.perform` re-reads the live CDP tree, resolves the node via `DOM.resolveNode`, and runs scroll-into-view + centre + `elementFromPoint` in one `Runtime.callFunctionOn` (so the point verified is the point clicked), then clicks it with Playwright's trusted, CDP-backed `page.mouse.click` — equivalent trusted input, headless or headed. COVERED raises `ElementCovered(role, text)` (carrying the layer, for 7c) and NOT LOCATED raises `ElementNotLocated`; both subclass `ActionError`, so today the explorer still records either as a skip until 7c catches `ElementCovered`. The context is pinned to a fixed 1280×800 viewport at device-scale 1. Pinned by `features/exploration_actuation.feature` (pure verdict) and `features/exploration_actuation_live.feature` (real browser: aria-label-only icon button clicked, below-the-fold element scrolled and clicked, covered element detected without activating the overlay, fixed viewport). First-cut limitations recorded honestly: duplicate role+name acts on the first in document order, and an element hosted in an iframe is not reached by the top document's `elementFromPoint`.

**7b — state settling (quiescence).** Before the explorer reads a state (for `state_id`, discovery, signal capture) or returns from an action, wait for the page to reach a stable rendering — DOM quiescence (no mutations for a quiet window) via a `MutationObserver`, i.e. wait for a *real signal that rendering stopped*, not a fixed sleep. A settle timeout is only a bounded safety net; if a page never settles the explorer **records that as a property of the state** rather than silently proceeding as if it had. The quiescence *policy* is pure logic behind an injectable clock (the `RunController` seam), testable in-process; the live glue (the observer + a bounded poll) is thin. This restores the reset-and-replay determinism the whole explorer rests on (discovered-element counts stop varying run to run).

*Shipped, with one scoping decision taken with the maintainer.* The live diagnostic exposed **two** coupled defects behind the shallow map, not one, so 7b delivers **settling + reset fidelity** together: (1) *Settling.* `spoor/exploration/settling.py` holds the pure quiescence decision — `wait_for_quiescence(*, observe, clock, sleep, quiet_window, timeout, poll_interval) -> SettleResult` settles once a monotonic mutation count holds steady for the quiet window and reports **unsettled** at a bounded timeout — driven by injectable `clock`/`sleep` (the `RunController` seam), so it is exercised deterministically with no browser (`features/exploration_settling.feature`). The live glue in `PlaywrightDriver` installs a `MutationObserver` mutation counter on every document (`add_init_script`) and a `_wait_for_settle()` polls it after each reset and each click; `state_html`/`ax_nodes`/`capture_signals` are called by the explorer right after those, so both reads and post-action returns see the settled page. A never-settling page is recorded — `StateSignals` gained a defaulted `settled: bool = True` that the driver flips to `False` on timeout, surfaced in the wiki as a "Did not settle" flag — and the run **proceeds on the last snapshot**; the earlier code path crashed (a reset that never reached `networkidle` raised straight through, aborting the run) or silently proceeded. (2) *Reset fidelity (the maintainer's decision).* A single browser context persists cookies and web storage across navigations, so a plain re-navigation lands on a *returning-visitor* render and reset-and-replay diverges from what discovery saw. `reset` now **clears cookies and both web-storage areas before navigating** (one context kept; only per-origin state wiped) and navigates with `wait_until="domcontentloaded"` + the settle wait rather than `networkidle` — so every reset is a true first visit and the `networkidle` crash is gone. Pinned live by `features/exploration_settling_live.feature` (reset clears cookies+storage → first-visit content; content rendered after the load event is discovered; a forever-mutating page is captured flagged unsettled, not fatal) and browser-free by `tests/test_exploration_driver.py` (post-click settle poll; reset clears cookies+storage then navigates, under a fake clock). Generic to every target (§0): one quiescence rule and one reset for every site; the fixtures merely stand in for persisted state, deferred render, and endless churn.

**7c — layer recovery.** For the genuine-interception category (7a's `elementFromPoint` check proved the target is covered), treat the blocking layer as its own state and interact past it toward making the originally-targeted action reachable — safety-gated (every engagement passes `evaluate_action`, so a layer whose only exit is a destructive action stays blocked outside a sandbox), bounded by *progress* (converge over steps, not a fixed retry), flagged with a real reason when it cannot be resolved (never a mute skip, never a loop), and with coordinate-level interaction available where DOM engagement can't clear it. `features/exploration_recovery.feature` already pins 7c's contract; 7a and 7b get their own features.

*Shipped.* The recovery is pure orchestration in `spoor/exploration/explorer.py`, browser-agnostic like the rest of the loop. A new `BrowserDriver.probe(action) -> ActuationVerdict` returns the actuation verdict (ACTUATE / COVERED / NOT_LOCATED) *without* clicking — `PlaywrightDriver.probe` and `.perform` now share one `_actuation` computation, so a probe can never disagree with the click that follows it. When `reach(action)` probes COVERED, it interacts past the layer with `next_layer_action`: the layer's *own* on-top actions are the discovered actions that themselves `probe` ACTUATE, gate-permitted and each fired at most once; after each it re-probes the target, converging when the layer clears (single-click), advances (multi-step), or the target uncovers, and giving up when no untried permitted on-top action remains (`_MAX_RECOVERY_STEPS` is a defensive cap, not the primary bound — the finite action set is). Because recovery runs inside `navigate`'s replay too, a covered state stays reachable on every reset-and-replay, not just the first visit. The §2e non-negotiable holds unchanged: a covering layer's destructive-only exit fails the gate, yields no candidate, and the covered action is flagged `blocked by an unresolved layer` (the destructive layer action itself is recorded as a skip); a genuinely missing element (NOT_LOCATED) is flagged `not located`, never mistaken for a blocker. Recovered edges are marked (`Transition.recovered_via`) and surfaced in the wiki ("Reached from behind a blocker"). Pinned browser-free by `features/exploration_recovery.feature` (blocker cleared with both actions behind it mapped; multi-step blocker worked through; destructive-only-exit stays blocked outside a sandbox; an unresolvable blocker flagged while exploration carries on elsewhere; a missing element flagged not-located) and live by its final scenario against `fixtures/static/explore_gated.html` (a full-viewport consent overlay intercepting every click → the site behind it is mapped and ≥1 action is recovered). Generic to every target (§0): the same discover + gate + probe recovers past every overlay; the fixture merely stands in for a launch dialog. *Coordinate-level interaction where DOM engagement can't clear a layer is deferred:* recovery drives the layer through its own discoverable actions, which cleared every overlay met so far; a layer with no discoverable clearing action is flagged blocked rather than brute-forced, and that limitation is recorded here honestly. Two further honest limitations: the clicks recovery fires to clear a layer are **not** counted against the run's request budget (the budget is checked once per walked action, and recovery is bounded per action by the finite layer-action set, so it adds only a constant factor — but the recorded request count understates the real click count on a heavily-overlayed target); and the kill switch is honoured at the next walked action, not mid-recovery (recovery is short and bounded, so this is at most a few extra clicks).

**7d — replay resilience (retry + fidelity check).** 7b restored reset-and-replay determinism for the *common* case (settling stopped discovered-element counts drifting run to run), but a follow-on diagnostic against the Juice Shop bench showed it did not eliminate the failure: under load the same reset still intermittently lands on a *degraded* render (Angular's "Force page reload" chunk-load fallback appears sporadically; the discovered action set flips 6 ↔ 7 even after settling). Reset-and-replay is all-or-nothing — one flaky step on the way to a leaf killed the whole subtree behind it — and the skip was mis-attributed to the leaf action rather than the replay step that actually failed. This slice makes replay resilient *and* honest.

*Shipped.* Purely in `spoor/exploration/explorer.py`, browser-agnostic like the rest of the loop; the `BrowserDriver` protocol is unchanged (it reuses 7c's `probe`/`reach` and `reset`). The replay path now carries the state id each step first reached (`_PathStep(action, to_state)`), so every reset-and-replay is **verified**: after `reset` the fresh page must equal the root state id, and each replayed step must land on the exact state id it first mapped to — otherwise the attempt raises an internal `_ReplayFailure`. `navigate_and_reach` **retries** a failed attempt up to `_MAX_REPLAY_ATTEMPTS` (3): a transient degraded render usually clears on the next reset, so coverage all-or-nothing replay used to lose is regained. When the attempts are spent the action is recorded as a skip with a reason that distinguishes a step that **stayed unreachable** (`replay could not reach …`) from a replay that **diverged** to a different state than first mapped (`replay diverged: …`) — never a mute skip, and attributed to the replay step that failed, not the leaf. A stably BLOCKED layer (7c's concern) is returned at once, not retried — there is nothing transient to wait out. Pinned browser-free by `features/exploration_replay.feature` (a transient miss retried so the state behind it is still mapped; a persistent miss flagged as an unreachable replay step; a replay landing on the wrong state flagged as divergence; a transient divergence retried) and live by its final scenario against a scripted loopback server whose entry page is served degraded on exactly one reset (retry meets a good render on the next reset and maps the page behind the flaky one). Generic to every target (§0): one verify-and-retry rule for every site; the fixtures merely stand in for a degraded render. Honest limitations recorded: (1) the fidelity check trades silent divergence for either retry-recovery or an explicit divergence-skip — on a genuinely jittery-render site where a step legitimately lands on different-but-valid states this could *reduce* recorded coverage versus the old ignore-divergence behaviour, so the effect on the Juice Shop bench is to be measured and reported, not assumed; (2) retry re-navigations are **not** counted against the run's request budget (same accounting gap as 7c recovery — the budget is checked once per walked action; retries add a bounded constant factor but the recorded request count understates the real navigation count on a flaky target); (3) the kill switch is honoured at the next walked action, not mid-retry (a retry loop is bounded by `_MAX_REPLAY_ATTEMPTS`, so at most a few extra navigations); (4) the *initial* reset at the start of the walk is not itself retried — if the very first render of the root is degraded the whole run starts from a poisoned root, which is out of scope here (a first-visit concern, not a replay one).

*Measured on the PrestaShop bench (7d limitation (1), reported not assumed).* Running `spoor explore` against the live PrestaShop storefront (§5.1) produced **6 states, 32 transitions, and 17 skips** — and **every one of the 17 skips is the 7d fidelity check** reporting `replay diverged: …` on the ever-present top-menu links (`Prices drop`, `HOME`). Root-caused with a normalized-DOM diff, not a guess: the target's *individual* pages are deterministic (the home page and the prices-drop page each hash to one stable `state_id` across every reset, direct navigation, and short click-path — normalization correctly absorbs PrestaShop's per-load randomness: random menu element ids, `static_token`, timestamps). The **listing pages are not**: `home → New products` lands on one `state_id` on most resets but intermittently on another. Diffing the two normalized structures (982 vs 1013 tokens) shows the difference is a JS-driven region that has not finished hydrating at capture time — one variant carries an extra `span[role=status]` (an ARIA live region / loading indicator), an extra `div[aria-disabled=false]` interactive block, and a different count of product `article` tiles. These are *genuinely different DOMs carrying state-bearing attributes* (`role`, `aria-disabled`), so state abstraction correctly refuses to merge them and the fidelity check correctly flags the replayed click as divergent. This is exactly the coverage-vs-fidelity tradeoff 7d predicted, now confirmed on a real multi-page site: the check behaved as designed (it converted a silent divergence into an honest skip) but capped the map at 6 states and cost 17 actions. The honest fix is **stronger capture-time quiescence detection** — wait for ARIA `role=status` live regions to clear and for the listing widget's DOM to stop mutating (a DOM-quiet + network-idle gate at capture) so both firings hash the fully-settled screen — *not* loosening state abstraction (ignoring `role=status`) or the fidelity check (accepting "any known state"), either of which would mask genuine divergence elsewhere. That is its own BDD-first §2e capture-settling slice (extends the 7b settling work); this note records the measurement, not a code change — the fix is **delivered as sub-slice 7e below**.

**Sub-slice 7e — settling also waits for the network to go idle.** *Shipped.* The fix the 7d PrestaShop measurement above pointed at, done at the source rather than by loosening state abstraction or the fidelity check. The pure quiescence decision (`spoor/exploration/settling.py`) gained an optional `busy: Callable[[], bool]` signal: the page counts as quiet only while `busy()` is false *and* DOM mutations have held steady for the quiet window, so a late network response that will still mutate the DOM cannot be settled past. Omitting `busy` is exactly 7b's DOM-only quiet (default `_never_busy`), so nothing that doesn't supply a network signal changes. `PlaywrightDriver` supplies it: it counts in-flight requests (up on `request`, down on `requestfinished`/`requestfailed`, floored at zero, and zeroed just before each awaited navigation and click so a leaked request can't wedge the count high) and passes `busy=lambda: self._inflight > 0` into the settle wait. The bound is unchanged and symmetric with 7b: a request that never completes (a long-poll, a hung fetch) makes the page *unsettled* at the safety timeout, exactly like a page that mutates forever — recorded on the state's `settled` flag, run proceeds on the last snapshot, never hangs. Pinned browser-free by `features/exploration_settling_network.feature` (an in-flight request holds the page unsettled until it completes, then settles under timeout; a request that never completes is reported unsettled at the timeout) and live by its third scenario (a loopback server whose entry page fetches a fragment the server delays past the quiet window — DOM-quiet alone would settle during the delay and miss it; waiting for the network to go idle means the fetched button is discovered). Generic to every target (§0): one network-and-DOM quiet rule for every site; the fixture merely stands in for a slow asynchronously-loaded page. *Measured effect on the bench:* re-running `spoor explore` against PrestaShop with 7e gave **7 states, 40 transitions, 0 skips** — against 7d's **6 states, 32 transitions, 17 skips** on the same target. All 17 divergence-skips are gone *and* coverage rose (more states and transitions mapped, since actions that were being skipped now fire), at a modest added settle wait (~0.75s per listing page, from the in-flight reproduction). The coverage 7d had been conceding to the capture-timing race is recovered. Honest limitations recorded: (1) the in-flight signal treats *all* requests alike — a site with a genuinely endless background request (analytics long-poll, a keep-alive stream, server-sent events) will now reach the settle timeout and be flagged unsettled where 7b's DOM-only quiet might have settled it, a deliberate trade of a slower, honestly-flagged capture for a correct one (the timeout bounds the cost); (2) the in-flight count is zeroed before each awaited action to prevent leaks, so a request still outstanding from *before* that action is not waited on — acceptable because each action's own settle waits out the requests it causes, which is what determines the state it lands on; (3) settle waits are still not charged against the run's request budget (the same accounting gap noted for 7c/7d).

**Sub-slice 7f — settling also waits out urgent live-region announcements.** *Shipped.* A third capture-timing race, found the same way 7d/7e were, this time on the Juice Shop bench (§5.1). The entry page renders, goes DOM-quiet *and* network-idle for several seconds, and only then removes a transient toast it showed on load — an `aria-live="assertive"` Material snackbar that auto-dismisses on a timer, with no network involved. So 7b's DOM quiet and 7e's network-idle both fire during that long lull: one capture includes the toast, a later one does not, the two land on different `state_id`s, and reset-and-replay (7d) flags a spurious "reset did not return to the start state" and skips the action. The measured symptom was a graph shape that reproduced across several main runs (`6/10/3/150`) and then drifted (`6/11/6/147`) on a run whose timing straddled the ~5.6s dismissal — a capture-timing race surfacing as apparent nondeterminism, not real drift, and it was the drift gate on the perf bench (§5.5) that caught it. The pure quiescence decision (`spoor/exploration/settling.py`) gained a second optional signal alongside 7e's `busy`: an `announcing: Callable[[], bool]` predicate. The page counts as quiet only while *neither* `busy()` nor `announcing()` is true and mutations have held steady for the window, so an urgent announcement still on screen holds the wait open exactly like an in-flight request does. `PlaywrightDriver` supplies it by querying for a non-empty `[aria-live="assertive"], [role="alert"]` element and passing `announcing=…` into the settle wait. The predicate is deliberately narrow (§0-clean — it keys on the ARIA standard, not on Juice Shop): `assertive`/`alert` mark an interrupting, by-nature transient announcement, whereas `polite`/`status` regions are commonly *durable* status — Juice Shop's own persistent cookie-consent banner is `aria-live="polite"`, and a broad "any live region" predicate was verified to hold the landing page unsettled forever (a regression, not a fix). The bound is unchanged and symmetric with 7b/7e: an assertive region that never clears makes the page *unsettled* at the safety timeout, recorded on the state's `settled` flag, run proceeds on the last snapshot, never hangs. Omitting `announcing` (the default) is exactly 7b/7e behaviour, so nothing that doesn't supply an announcement signal changes. Pinned browser-free by `features/exploration_settling_announcements.feature` (an assertive announcement showing until 600 ms holds the page unsettled past the quiet window then settles under timeout; one that never clears is reported unsettled at the timeout) and live by its `@browser` scenario (a loopback server whose entry page shows an assertive toast carrying a button and removes it on a timer past the quiet window — DOM-quiet alone would discover the button; waiting the announcement out means it is gone by the settled read). *Cost, recorded honestly:* the wait now sits through the full announcement lifetime, ~5.8s per reset on Juice Shop where the snackbar dismisses on a ~5.6s timer, taking the bench run from ~90s to ~7.3min — a deliberate trade of wall-clock for a shape that genuinely reproduces, made by explicit human decision when the alternative (loosening the exact-match drift gate to tolerate the race) was rejected. This also revises the §5.5 premise below: graph-shape counters *do* reproduce against a live SPA once the settle path waits out every source of post-load change, but only then — the gate is what proved they hadn't been. Known separate issue, not addressed here: the `/#/about` page runs a genuinely periodic CSS carousel (`slide-in-left`/`slide-out-right`) that is not a transient announcement and is out of 7f's scope.

**Design (not yet built) — §2e second-round interactive exploration: a map-generated config, subtractive permissions, sandbox-only destructive scope.** Exploration mode above (slices 6–8) is read-only: it discovers, observes, and maps, but never types into a field, logs in, or fires a destructive action outside a sandbox. This note captures the agreed shape of the *next* exploration capability — a **second, opt-in round** that goes further using a **config the first run generates for that specific site** — so the design and, above all, its safety boundary are locked in before any code. It is not built yet; when built it follows the BDD-first workflow like everything else, and it stays gated behind the read-only-mode-exit prerequisites already tracked in §9 (keyword-list localization, input-data provisioning). It pairs with the anchored depth-relative *resume* capability in the design note immediately below — the two are the intended shape of §2e "v2."

*The loop.* Round one is today's read-only autonomous crawl, producing the state-action map (§2e) and wiki. From that map Spoor **scaffolds a starter config matched to the site**: the actions it discovered, the input fields it saw (each with an inferred type/generator and an example, per the §9 input-data-provisioning seam), the points where a login is required, and every action its safety heuristic flagged destructive (and whether it was skipped for being off-sandbox). The user reviews and fills that config — supplying a session, pinning specific input values, and opting in per-action to what round two may touch — and round two re-runs, now able to authenticate, fill forms, and (only where the sandbox rule already allows it) exercise state-changing flows, complementing the map with the states only reachable past a login or a form.

*§0 stays intact.* The generating and consuming *mechanism* is generic — it reads the map's own generic facts (roles, field semantics, ARIA) and emits a config the same way for every target; nothing about a specific site is baked into `spoor/`. The **filled config is site-specific data**, the identical sanctioned escape hatch a §2a extraction config or the per-domain cache already is — so this adds no site-tailoring to Spoor itself, exactly as intended.

*The safety boundary — unchanged, and the crux of this note.* The §2e destructive-action non-negotiable is **not** relaxed by any of this:

- **Permissions are subtractive only.** The per-action opt-in is an *allowlist that can only narrow* the built-in safety guard, never widen it. It cannot authorize an action the guard forbids; the guard stays the ceiling, the config only ever the floor.
- **Destructive actions stay sandbox-only and non-configurable (§2e).** On a registry-matched sandbox (`localhost`/`127.0.0.1`/`sandbox: true`) round two may fire flagged-destructive actions — the guard already permits this, so a permission config there needs no rule change. On any **non-sandbox** target those actions remain *always skipped and logged*, regardless of what the config says. Enabling destructive actions on a real production site would require an explicit, separately-recorded amendment to the non-negotiable — a maintainer decision this note deliberately does **not** make; it is called out here so it can never happen by the quiet accretion of a config field.
- **Auth is bring-your-own-session (§2h), not automated login.** Round two authenticates by consuming a supplied storage-state file (the shipped `session:` path), never by Spoor driving an SSO/MFA flow (declined in §2h as per-provider and §0-hostile). *Filling* a login form with user-pinned credentials is ordinary form-filling — interaction, gated by the same sandbox/keyword rules as any other input, not a special case.
- **Input-data and redaction rules carry over.** Values come from the §9 input-data seam (generic semantics-driven generation + user-pinned specifics); a config may hold real credentials/PII, so §2h redaction governs anything of it that reaches a shared surface, and pinned secrets stay local. The §2e run-level budget and kill switch apply to round two unchanged.
- **Keyword-list localization (§9) binds here too.** Because round two leaves read-only mode, the destructive-keyword guard must be locale-aware and err-safe first (treat an uncovered locale as "assume destructive / skip") — the same §9 prerequisite that gates Phase 5.

*What round two adds, concretely.* Three complementary modes, each opt-in and each inside the boundary above: an **authenticated deeper map** (a session reaches states behind a login the read-only round couldn't); **interactive form-driven exploration** (pinned/generated input data lets it fill search, filters, and multi-step forms, discovering states gated behind a submit); and, **sandbox-only, state-changing coverage** (against a sandbox target it can exercise cart/checkout/CRUD flows the guard already permits, mapping what the read-only round had to skip). The generated config is what makes all three reviewable up front: the user sees exactly which actions and fields a second round *could* touch, and every destructive one it flagged, before opting in to any of it.

**Design — §2e anchored, depth-relative resume: complement a map from a chosen state outward.** The companion to the second-round note above, and the other half of §2e "v2." Today an exploration run starts from the root and crawls to a global depth/state budget; a re-run starts over. This capability lets a subsequent run **begin from a state the first run already reached** and explore a bounded depth *outward from that anchor*, merging what it finds into the existing map — so mapping a large product becomes incremental and focused (deep-dive one area) rather than an all-or-nothing re-crawl. It reuses machinery that already exists — reset-and-replay drives to any recorded state (§2e 7d, by BFS over the recorded edges from root), depth-bounded traversal already caps the frontier, and the graph is persisted and servable (§2f) — so the new parts are anchor selection, re-origining depth at the anchor, and an additive merge. Built incrementally, BDD-first (see the shipped decision note below). Read-only-safe on its own (it discovers and maps, no interaction), so unlike the second-round note it carries no new safety-boundary exposure; the two compose (a resume run can also *be* an authenticated/interactive second round, each constraint applying exactly as written there).

*Anchor selection — configurable addressing, never an interactive picker.* An anchor is named in config/CLI and resolved against the persisted map by a small **state-selector** layer, generic to every target (§0). Four selector kinds, combinable: `title:` (the wiki's human-readable state title), `url:` (the route the state lives at), `id:` (a git-style state-id prefix), and `path:` (the action sequence that reaches it — the same replay path reset-and-replay drives). Resolution is **deterministic and never guesses**: a selector matching exactly one state anchors there; one matching several is an *error that lists the candidates* (id + title + url) to narrow — the same "never fabricate" stance the serving layer takes for an unmapped URL — and selectors may be combined to disambiguate. A GUI picker is explicitly *not* this (that stays the far-horizon §9 GUI marker); Spoor is config/CLI-driven.

*What's resolvable today vs. what needs a persistence extension (recorded honestly).* The persisted map (§2f `shareable_exploration_map`) currently carries, per state, only the canonical **id** and the discovered **action inventory** (role + name) — **not** titles or URLs. State identity is deliberately DOM-only (a state carries no URL), and the wiki title is computed at *render* time from the captured `document.title`, never stored on the node or in the shareable projection. So `id:` and `path:` resolve against the persisted map as-is; **`title:`** needs the (already-redacted) title added to the shareable projection — cheap and §2h-safe, since the wiki already redacts it; and **`url:`** needs a prior decision, because no observed per-state URL is persisted today and introducing one touches the DOM-only identity model (the URL is currently transient walk state, used only in the frontier dedup key). The **pure selector resolves all four kinds** over an in-memory candidate set regardless; wiring each kind to the persisted map is gated on that field being available there — so the buildable-first slice is the pure resolver, then the projection extension for `title:`, then the `url:` design decision, then the resume traversal itself.

*Relative depth.* Depth is re-origined at the anchor: the anchor is depth 0 and the existing `--max-depth` bound is measured outward from it (explore N actions deep, backtrack, take the next branch, all capped at N from the anchor). No new traversal semantics — the same bounded frontier, its origin moved from root to the chosen state. The run-level budgets and kill switch (§2e) apply unchanged.

*Merge and staleness — fail loud, never fabricate.* Resuming replays the recorded path to the anchor (reset-and-replay), then explores outward and **merges additively** into the existing map: new states and transitions are added; states already present are left as they were. The honest failure mode is a **stale map** — the site changed since round one and the path no longer replays to the same state id. That is reported as a stale anchor and the run stops; it never silently re-explores from root, and never fabricates a match. Re-verifying or refreshing an already-mapped state is the §2f freshness concern (backlogged, §9), deliberately out of scope here — this capability *adds* coverage, it does not re-check what's already mapped.

**Decision — §2e resume, shipped (four slices, buildable-first order above).** The resume capability shipped in the four slices the design note ordered. **(1) Pure resolver** — `spoor/exploration/selector.py` resolves one or more constraints (`IdPrefix`/`TitleIs`/`UrlIs`/`PathIs`, combinable with AND) against a candidate set, returning resolved / unmatched / ambiguous-with-candidates; `parse_selector` reads the flat `kind:value` CLI form for the three single-value kinds (a `path:` is built structurally, since an action name can hold `:`/`=`/`>`); it never guesses (`exploration_state_selector.feature`). **(2) Graph candidate adapter** — `selector.graph_candidates(graph)` turns each in-memory state into a candidate (id, redacted title, root-relative `path` via the new `graph.paths_from_root`); `url` stays `None`, pinned honestly (`exploration_graph_candidates.feature`). **(3) Persisted-map loader** — `spoor/exploration/persisted_map.py:load_exploration_map` reconstructs an `ExplorationGraph` from the §2f shareable projection (ids in order, action inventory, topology, skips; no signals, so `title:` does not resolve against a saved map), validated by a real project-then-load round-trip (`exploration_persisted_map.feature`). **(4) Resume traversal** — `spoor/exploration/resume.py:resume_exploration` ties the three together (load → build candidates → resolve → crawl) and `explorer.explore` gained `resume_from`/`resume_anchor`: it starts from the loaded graph, seeds the breadth-first walk at the anchor with the root-relative reset-and-replay path (reconstructed by the new `graph.path_steps_from_root`, which keeps each step's landed state so replay can verify it), **re-origins depth at the anchor** (`len(path) - len(seed_path)`, so the anchor is depth 0 and `--max-depth` counts clicks from it), and **merges additively** — a transition-existence guard means a resume that re-fires an already-mapped edge does not duplicate it, and a fresh crawl (which fires each edge once) is unaffected. It **fails loud**: a selector matching no state or several raises `ResumeError` (the several case lists candidates); a start page whose id no longer matches the saved map's root, an anchor unreachable from that root, or a path that will not replay within the retry bound raises `ValueError` — never a silent remap. The CLI exposes it as `spoor explore <url> --resume-from <selector>` (loads the URL's saved map, refuses before launching a browser if none exists, and writes the merged map back). `exploration_resume_traversal.feature` pins the fast-tier chain (discovers states beyond the anchor, preserves the earlier map, measures depth from the anchor not the root, resumes from the root, and both fail-loud paths) and a `@browser` scenario proves the whole load→resolve→resume→discover cycle end to end in real Chromium over an A→B→C fixture. **Still deferred** (design note above): adding the redacted `title:` to the shareable projection so `title:` resolves against a saved map, and the `url:` per-state-URL decision; from a *saved* map the CLI therefore anchors by `id:` today. Generic to every target (§0): one resume path for all.

## 2f. Serving the map: MCP server & API (the hero-sentence promise)

Everything in §2a–§2e produces a map — extracted fields, the API surface, the signals catalog, the exploration-mode state graph. §2f is what turns that from "files on disk" into something an *agent* can actually consult: "give your agents a map of the web," not just "give a person a wiki to read."

Two consumption modes, both thin layers over data structures the rest of the plan already produces — no new capture/analysis logic here, purely serving what's already been built:

- **MCP server mode.** Spoor runs as an MCP server (using Anthropic's official `mcp` Python SDK) exposing tools like "get the known state/behavior for this URL," "list the actions available from this state," "what does the API surface look like for this domain," "has this product's checkout flow been mapped already." An agent — Claude or otherwise — can consult Spoor's existing map instead of burning its own tokens re-discovering a site's behavior from scratch every session. This is the direct payoff of §2b/§2c/§2e: the whole point of capturing all that signal was so it doesn't have to be rediscovered live each time.
- **Plain API mode.** The same underlying data served as a conventional REST API (FastAPI is the natural fit — async-native, pairs cleanly with the rest of the async stack, MIT-licensed) for consumers that aren't MCP clients: scripts, dashboards, CI checks against a previously-mapped site.

**Freshness, explained plainly.** Say Spoor mapped a site's checkout flow on Monday. On Friday, an agent asks Spoor "what happens when I click checkout" — but the site may have changed its checkout page since Monday, and Spoor wouldn't know unless it re-checked. "Too old" is just: at what point should Spoor say "let me re-verify that" instead of confidently handing back Monday's answer as if it were still true right now? The per-domain cache (§2) already tracks when something was last confirmed, so the mechanical part (attaching that timestamp to every served answer, and giving the caller a way to force a re-check) is easy. **The actual policy — how old is "too old" before Spoor should recheck on its own rather than wait to be asked — isn't decided, and doesn't need to be right now.** Backlogged (see §9); a reasonable placeholder is "always show the age, never auto-recheck in v1," deciding the smarter policy once there's real usage to learn from.

**Sequencing.** This depends on §2a (extraction) and §2b (API surface) existing to have anything worth serving, but not on §2e (exploration mode) — an MCP/API layer over "the fields and API surface from a configured run" is useful on its own, well before the full autonomous exploration graph exists. Reasonable to build a first pass alongside Phase 4 (packaging) as v1 scope, with the richer "serve the full exploration graph" version arriving once §2e (v2) ships.

**Decision — §2f first slice (read-only REST API over a captured map).** With Phases 1–3.5 stable, §2f begins with its plain-API mode — the thinnest useful serving layer — rather than the MCP mode, because it is straightforwardly testable in-process (a FastAPI `TestClient`) and shares the exact store/service the MCP mode will later sit over, so nothing is thrown away by starting here. Two pieces: (1) `spoor/serving/store.py:MapStore` — a persisted per-domain map (`maps/<domain>.json` under the git-ignored cache root, the same local-first home as the fingerprint/change-detection stores). A run records its extracted records for the target URL there with a UTC capture time; a missing/corrupt file is "nothing mapped yet", never an error. It holds the **same records the output pipeline already writes to shared output** — not a raw local-only capture (HAR/storage state), which never enters it (§2h). The CLI's `run` populates it after each run; a new `spoor serve` command serves it. (2) `spoor/serving/api.py:create_app(store)` — a FastAPI app exposing **only** `GET /healthz`, `GET /domains`, and `GET /map?url=…`. **Read-only is structural, not disciplinary (§2f/§2h non-negotiable):** the app defines no non-GET route, and `serving.feature` pins this with a scenario asserting every route's methods are a subset of `{GET, HEAD}`. Every `/map` answer carries `captured_at` and a computed `age_seconds`, realising §2f's "always show the age" — the **v1 freshness policy is "never auto-recheck"**, and a **force-recheck** endpoint is a deliberate follow-on (§9), as is the **MCP server mode**. Because §2h names an API response as a shared surface, served record values pass through the secret-redaction primitive (`spoor/security/redaction.py`) on the way out — the local store may hold raw records, but the serving boundary is redacted, and `serving.feature` pins this with a scenario asserting a bearer token in a served record leaves as `[REDACTED]`. Serving dependencies (FastAPI, uvicorn) are an optional `serve` extra, kept out of the dependency-free core (§1) — only `spoor serve` needs them. **Deferred at this slice, built later:** the force-recheck seam (now shipped — see the force-recheck decision below).

**Decision — serve the observed API surface alongside records (§2f, §2h split preserved).** The `/map` answer now also carries the run's observed **API surface**, but only the §2h-shareable projection of it, mirroring the observability layer's own split: the published spec (`kind`/`version`/`url`) and GraphQL endpoint (`url`/`types`) are non-sensitive and served **whole**, while the *synthesized* spec and *action correlation* are reduced to **counts only** (`endpoint_count`/`request_count`, `action_count`/`request_count`) — their templated paths and local-only `doc_path` can embed an un-clustered secret segment, so they never enter the served surface at all. `spoor/serving/store.py:shareable_api_surface(...)` is the one place that projection is made (the CLI's `run` calls it, storing the projection, never the raw dataclasses), and the API runs it through the same redaction guard on the way out (counts untouched; a secret-shaped URL redacted like any shared string). `serving.feature` pins both halves: the spec/GraphQL/synthesized counts are served, and the served payload exposes no templated endpoint path.

**Decision — MCP server mode (the second §2f consumption mode, read-only always).** Beside the REST API, §2f now ships its MCP mode: `spoor/serving/mcp_server.py:create_mcp_server(store)` (using the `mcp` SDK's high-level `MCPServer`), and a `spoor serve-mcp` command running it over stdio for a local agent. It sits over the **same** `MapStore` and answers with the **same** view as the REST surface — the two modes were deliberately factored onto one shared `views.map_view(entry)`, so the freshness age and the §2h redaction of records + API surface are computed in exactly one place and neither mode can drift from the other. **Read-only is the non-negotiable, enforced two ways:** only read tools are registered (`list_mapped_domains`, `get_map` — no tool changes a target or the stored map), and each carries the MCP read-only / non-destructive annotations; `serving_mcp.feature` pins it with a scenario asserting the exposed tool set is exactly that allowlist and every tool is marked read-only and non-destructive. An unmapped URL is a tool error, never a fabricated answer (parity with the REST 404). The `mcp` SDK joins FastAPI/uvicorn in the optional `serve` extra — the core engine never imports it; only `spoor serve-mcp` and the serving tests do. **Now shipped (was deferred here):** the force-recheck seam — see the decision below.

**Decision — force-recheck seam (opt-in, read-only *with respect to the target*).** §2f said a caller may force a re-check; this ships it, on both surfaces. The subtlety is the §2f/§2h non-negotiable: the serving layer must never cause a *state-changing or destructive action on a target*. A recheck doesn't — it re-runs the URL's own extraction, which is the same **read/observation** a normal run performs — so the non-negotiable, which explicitly permits *triggering a new read/observation run*, is honored. The guarantee was therefore **reframed from "no non-GET route / read-only tools only" to "no route or tool changes a target"**: a plain reader server stays GET-only (REST) / read-tools-only (MCP), and enabling recheck adds *exactly one* seam — `POST /map/recheck?url=…` on REST, a `recheck_map` tool on MCP — whose sole effect on the target is to observe it. That MCP tool is **honestly annotated**: `read_only_hint=False` (it fetches and rewrites the local map) but `destructive_hint=False` — no tool on the server is ever destructive to a target. Mechanics: the store now persists the serialized `ExtractionConfig` each entry came from (**local-only — never projected into `map_view`, so it never reaches a served response**), and `spoor/serving/recheck.py:recheck_url(store, url)` reconstructs that config, re-runs `extract.run_report`, and re-records the fresh result; an unmapped URL (or one recorded before configs were persisted) is a 404 / tool error, never fabricated. Both surfaces gain a `--recheck` opt-in flag on `spoor serve` / `serve-mcp`, **off by default**. `serving.feature` and `serving_mcp.feature` pin both shapes (plain server unchanged; recheck-enabled server adds exactly the one seam, non-destructive, and honestly non-read-only on MCP). This is the *mechanical* force-recheck only; v1 still **never auto-rechecks** — the "how old is too old" policy stays backlogged (§9).

**Decision — serve the exploration graph (§2f, the "serve the full exploration graph" step §2f's sequencing named).** With §2e's exploration mode complete (state-action graph + wiki), §2f now serves that graph too, closing the hero-sentence promise for exploration mode: an agent can consult "what happens when I click X" as data, not just read a static wiki. Built the same way the API surface was: (1) `spoor/serving/store.py:shareable_exploration_map(graph)` — the one place the graph is projected to §2h-shareable facts, mirroring `shareable_api_surface`. It reduces to plain strings/ints/bools/lists so `map_view` redacts it wholesale: per state, the abstract id, the discovered action inventory (role + name), and the free-signal bundle **as counts only** (raw console/storage/network *values* captured at a state stay local-only, the same counts-only stance the synthesized API surface takes); per transition, the from/to ids, the action fired, and **what it changed** — the before/after signal diff, carried *with* its added values (console lines, storage keys, request URLs), because that diff is precisely the "what did clicking X change" answer §2f exists to serve, and each value is a plain string redacted on the way out; plus every safety-gate skip with its reason, and the three counts. Returns None for an empty graph (nothing to serve), the same no-shell stance as `shareable_api_surface`. (2) A new local-only-then-redacted `MapEntry.exploration` field with store round-trip, surfaced by adding one line to the shared `views.map_view` (`redact_value(entry.exploration)`) — so **both** the REST `/map` and the MCP `get_map` serve the exploration graph for free, redacted identically, neither able to drift. (3) `spoor explore` now records its graph into the map after each run (records empty, no tier — an exploration-only entry), so the capability is end-to-end: explore a site, then serve its graph. `serving.feature` and `serving_mcp.feature` each gain a scenario asserting the graph is served with the right counts/action label and that a secret captured in a signal leaves as `[REDACTED]`; `exploration_browser.feature` gains a scenario asserting a live `spoor explore` run persists a servable graph; and `tests/test_serving_store.py` pins the projection's shape, its counts-only per-state split, its actual-diff per-transition payload, and its empty-graph/None-signals contracts directly. Read-only w.r.t. the target is untouched (a graph is read back from the local map; no new route or tool, no target interaction) and §2h redaction is enforced at the one shared boundary.

## 2g. Test automation run generation (HT's own primary use case)

This is the concrete shape of "test automation run creation" from HT's own stated needs: a captured map (a configured §2a run, or a full §2e exploration graph) is a **golden-master record of known-good behavior** — state X, action Y, produced signal bundle Z. That's already 90% of what a regression test asserts; §2g is the last-mile step of exporting it as one.

Two output shapes, both generated, never hand-written:
- **Assertion-style regression tests**: for each captured transition, emit a test (pytest, or a Playwright Test file if the consuming team is JS-based) that replays the action and asserts the resulting signal bundle still matches — the DOM state, the API calls fired, the console being clean, whatever the capture included. Re-running these against the real product later is exactly how drift gets caught: a failing generated test means the product's actual behavior no longer matches its last-known-good map.
- **Human-readable test plans**: the same transitions rendered as a plain-language run sheet (ties into the §2e wiki output) for teams that want a reviewable test case, not just executable code.

This depends on §2a/§2e existing (nothing to generate from otherwise) and is a natural companion to §2f rather than a separate subsystem — both are "consume the captured map," just for different audiences (an agent asking a question live, vs. a generated artifact a CI pipeline runs). Sequencing: a first pass makes sense alongside Phase 5 (§2e, v2), since the richest version needs the full exploration graph — a thinner version scoped to just a configured §2a run's captured transitions could ship earlier if HT's own test-automation need turns out to be more urgent than the v2 timeline implies (worth revisiting once Phase 1–3.5 are stable and this becomes concrete rather than aspirational).

**Decision — §2g sub-slice 2g-i (pure pytest generator from the exploration graph), shipped.** The first §2g slice delivers the assertion-style output shape against the §2e exploration graph, built logic-first exactly as the wiki renderer was (6a): `spoor/testgen/pytest_gen.py:build_tests(graph, *, target) -> dict[str, str]` maps a graph to pytest test *sources* (filename → code) with **no browser and no disk** — the thin on-disk writer and a live "the emitted suite runs green against a fixture" proof are the follow-on sub-slice 2g-ii. Per mapped transition the generator emits a `test_transition_N.py` that, via a shared `_spoor_testkit.py` and a `conftest.py`, drives **Playwright** to replay the reset-and-replay path that reached the transition's from-state (reconstructed by a BFS over the recorded edges from the root state), fires the action, and asserts the additive signals the transition was recorded to add (console lines, storage keys, request URLs) still appear — a real regression test run against the live product, chosen over a data-only self-consistency check because catching product drift is the stated need. Two consequences recorded as deliberate, not gaps: **(1)** because a generated test is a **shared-output surface**, §2h redaction is mandatory on every captured value baked in, *and* — unique to testgen — the emitted suite must redact the live values it observes (`redact_all`, importing Spoor's own `redact`) before comparing, so both sides match like-for-like and no raw secret is ever the expected literal; this makes running the generated suite depend on `ht-spoor` + `playwright`, accepted because the §2h-safe alternative (baking the raw secret in so the assertion matches) is a non-negotiable violation. **(2)** Only the additive string signals are asserted; the a11y-node delta and screenshot hash are deferred (reproducing them in the generated runtime needs Spoor's CDP a11y read and visual hasher — the same staged deferral the wiki took for screenshot images), and an action whose accessible *name* is itself a secret gets redacted so its locator would not match live — accepted as rare (names are UI labels) over writing the raw name. Nothing is site-specific (§0): one emitter for every target. `features/testgen.feature` (6 scenarios) and `tests/step_defs/test_testgen_steps.py` pin the generated sources — valid Python, one test per transition, path replay, fire, per-signal assertions, the no-change smoke test, redaction, and the empty-graph→no-tests contract.

## 2h. Data handling, security & auth (core architecture, not later hardening)

This section exists directly because of the bottom-line critique: destructive-action safety was already treated as core (§2e), but everything about *data* sensitivity — where captured cookies/tokens/HAR/screenshots live, whether secrets get redacted, what an MCP-connected agent is allowed to do, how login-gated targets are handled at all — was drifting toward "backlog" by omission. These are now decided, folded into the base design rather than appended after the fact.

**Storage & redaction (decided): local-only, auto-redact.** Every artifact §2c/§2d capture produces — cookies, tokens, full storage state, HAR files, screenshots, console output — stays on the user's machine under a per-run directory, never transmitted anywhere by default; this is the literal, concrete meaning of "local-first," not just a slogan. Before anything is written to a *shared* surface — the §2d output pipeline (JSONL/CSV/SQLite), the §2e wiki, or a §2f MCP/API response — Spoor scans for known secret patterns (bearer tokens, common auth-cookie shapes, API keys matching common vendor formats) and redacts them. The raw, unredacted capture (full HAR, full storage state) lives in a separate local cache directory that's never included in anything shared, exported, or served by default — exporting that raw cache is a separate, explicit user action. The actual redaction pattern list is a real Phase 2.5 deliverable, not a vague promise — tracked in §9 below rather than assumed to already exist.

**MCP/API permission boundary (decided): read-only, always.** The §2f serving layer only ever answers questions about a previously-captured map, or triggers a new *read/observation* run (a §2a config or a §2e exploration) — it never exposes a tool letting an agent directly cause a destructive or state-changing action on the target. This is a hard boundary on the MCP/API surface specifically, in addition to (not instead of) §2e's sandbox-only rule for destructive actions during exploration itself: an agent consulting Spoor can look, and can ask Spoor to go look again, but can never use Spoor as a channel to change anything on the target.

**Auth, login, MFA, SSO, multi-role (decided, deliberately scoped narrow for v1): bring-your-own-session (implemented).** Spoor does not implement login flows, MFA handling, or SSO redirect automation itself — that's a large, fragile, per-provider surface that would violate §0's no-tailoring principle almost by definition, since every SSO provider ends up being its own integration. Instead, the user authenticates manually once (in their own browser, or Spoor's) and supplies the resulting storage state (`context.storage_state()` — the same shape the §2c capture writes) as an input to a run. Multi-role support is just running the same config once per supplied storage-state file, one per role. This keeps auth entirely outside Spoor's core surface while still making authenticated targets usable from day one.

Delivered as the `session:` config field (a path to a storage-state JSON), loaded by `spoor/security/session.py` — the §2h owner of this secret-bearing input, not `core/` (§0): `load_session` validates the file (a missing/malformed/wrong-typed file raises `SessionError` *before* any fetch, so a run fails loudly rather than silently proceeding anonymous), and the tiers consume it generically. The static tier (tier 1, no JS) sends the session's **cookies** via the httpx jar with their original domain/path scope; the browser tier (tier 2) hands the whole file to `browser.new_context(storage_state=...)` so Playwright applies **cookies + per-origin localStorage**. A target gated behind a localStorage token yields zero records at tier 1 and escalates to the browser, which reaches it — no config author choice, pure dispatcher escalation (§2). The supplied state is never echoed to shared output (it is loaded into the fetch, not captured from it), so redaction — which guards *captures* on their way out — is not in play; the discipline that applies is simply that `RunResult`/`RunSummary` carry nothing from it. Covered by `session.feature` (both tiers + the loud-failure path) and `tests/test_session.py` (loader boundaries).

**Decision — Phase-1 run-observability slice (pulled forward).** §2d lists run observability among the operational essentials but the phased plan grouped it loosely with the Phase-3.5 items; it is pulled forward into Phase 1 by maintainer direction, because it builds directly on the escalation dispatcher just landed and closes the "did this run actually go well?" gap §2d names, with no new machinery. The slice ships a structured, operator-facing `RunSummary` produced for every dispatched run, reporting only what the current machinery can honestly derive: **items scraped, pages fetched, the tier that resolved the run, the escalation path (tiers attempted, so "escalated tier 1 → tier 2" vs. a capability-routed single tier is visible), and blocked URLs.** The §2d items that need absent machinery are deliberately **not** faked: error/retry classification waits on the Phase-3.5 retry mechanism, and "which fields fell back to tier 3/4" waits on those tiers existing. Placement follows the §0 layout: the raw per-run facts (`tier`, `pages_fetched`, `tiers_attempted`) are stamped on `RunResult` by the dispatcher in `spoor/core/extract.py`, and the operator-facing summary object plus its rendering live in `spoor/operational/observability.py` — core produces the signals, `operational` presents them. The CLI prints the rendered summary after each run; `RunSummary` stays a plain structured object so a later phase can serialize it (the §2d "signals-catalog thinking turned inward") without rework.

**Decision — Phase-2.5 HAR-capture first slice (pulled forward, local-only).** HAR recording — "wire in HAR recording on every Playwright context (near-free once Phase 1 exists)" (§2b/§2c) — is started early, by maintainer direction, as the concrete foundation the §2c signal catalog and the mitmproxy2swagger spike (§8.4) both build on. Scope of this slice, deliberately tight:

- **Opt-in this slice, via `capture.har: true` on the §2a config** (a new `Capture` model, `extra="forbid"` like the rest). §2c's eventual *default-on* capture is the full Phase-2.5 target and is **not** turned on here — an existing run's behavior is unchanged unless it asks for capture, so nothing starts silently writing files.
- **Browser-tier only.** Only tier 2 has a Playwright context to record; a run that resolves at tier 1 (no browser) produces no HAR, and the run summary (§2d) says so honestly rather than writing an empty file. A tier-1 static fetch's single request is not the target of network capture.
- **Raw, local-only — never the shared path (§2h non-negotiable).** The HAR is written to a per-run subdirectory of a local-only cache dir (`.spoor-cache/<run-id>/network.har`, git-ignored), exactly the "raw, unredacted capture lives in the local-only cache" surface §2h describes. It is **not** routed through the output pipeline, the wiki, or any MCP/API response, so the redaction-before-shared-output rule is not in play for it — and must never be bypassed by later routing a raw HAR to a shared surface without the explicit-export step. The per-run cache dir helper lives in `spoor/security/` (the §2h data-handling owner). A configurable cache base and default-on capture are deferred to the full Phase 2.5.

The captured HAR path is surfaced on the run summary so an operator can find it. This slice adds no new runtime dependency (Playwright already records HAR natively via `record_har_path`).

**Decision — secret-redaction pipeline (the §9 pattern-list deliverable, built as a reusable primitive first).** The §9 backlog names a "concrete secret-redaction pattern list" as a Phase-2.5 prerequisite before any capture surfaces raw values to shared output. It is built here as its own slice — `spoor/security/redaction.py`, a pure `redact(text) -> str` primitive over a maintained `SECRET_PATTERNS` list — *before* its first consumer, so the consumer (client-side storage state, the next slice) inherits a tested guard rather than growing an ad-hoc one. Scope and boundaries, deliberately explicit so the claim isn't oversold:

- **Default-on, no opt-out (§2h non-negotiable).** `redact` takes only the text; there is no parameter to disable it. A caller on the shared path cannot ship raw secrets through it. The only way raw values leave the machine stays the separate, explicit export of the local-only cache — which does not route through redaction.
- **Known shapes, not entropy.** The list redacts *recognized* formats: auth-scheme credentials (`Bearer …`, and `Basic …` when it rides an `Authorization`/`Proxy-Authorization` header — anchored there because "Basic" is also an ordinary English word, unlike "Bearer"), common auth/session-cookie *and* secret field names keeping the name and redacting the value (`sessionid`, `access_token`, `csrf_token`, `api_key`/`apikey`, `client_secret`, `api_secret`, `token`, `id_token`, `password`/`passwd`/`pwd`, …), common vendor API-key formats (OpenAI `sk-…`/`sk-proj-…`, Stripe secret/restricted `sk_live_…`/`sk_test_…`/`rk_live_…`, AWS `AKIA…`, Google `AIza…` and OAuth `GOCSPX-…`, GitHub `ghp_`/`github_pat_`, Slack `xox[baprs]-…`), JWTs, and PEM private-key blocks (`-----BEGIN … PRIVATE KEY-----`). It is **not** a general high-entropy detector — that trades false positives (mangling legitimate data) for a promise this layer does not make. A keyless high-entropy blob with no recognizable shape — the canonical example being an AWS *secret* access key (40 base64 chars, no prefix) — is deliberately **not** caught here; the local-only cache, not redaction, is what keeps such raw captures off shared output. This bounds the claim honestly, the same discipline §5/§6 apply to tier-3 accuracy and tier-4 stealth. The vendor forms above were widened after an adversarial false-negative probe found the earlier `sk-…`-only rule missed Stripe's underscore keys and OpenAI's `sk-proj-` form; the probe was distilled into `redaction.feature` scenarios so those gaps stay closed.
- **Structure-preserving and idempotent.** A non-sensitive prefix (auth scheme, cookie name) is kept; the `[REDACTED]` placeholder matches none of the patterns, so re-redacting is a no-op. The list is extended deliberately, with a fixture example in `redaction.feature` for every shape added — never a broad catch-all.

**Decision — the extracted-record path is wired to redaction (closing the last §2h shared-output gap).** The primitive above was first wired only to the storage-state signal; the primary **extracted records** — the thing the §2d output pipeline writes to a file and the §2f serving API returns — were still surfaced raw. That was the §2h non-negotiable's own listed surface ("before anything reaches the output pipeline … or an MCP/API response") left unenforced, so it is now closed. A shared record-level helper, `redaction.redact_records(records)` (walking every string value, including nested lists/dicts; numbers/`None`/booleans pass through; idempotent), runs **on by default, no opt-out** at both boundaries: `output.write_records` redacts after schema-validation and before any write, and the serving API redacts on the way out. The raw records still live only in the local-only cache and the per-domain map; only the redacted form reaches a file or an API response. This is the documented known-shapes/false-positive tradeoff applied to primary data: a scraped field that happens to hold a recognized secret shape is redacted (accepted), while a keyless high-entropy value is not (unchanged) — the same boundary the primitive draws everywhere. `output.feature` and `serving.feature` each pin a scenario proving a bearer token in a record leaves as `[REDACTED]`.

## 3. License

**Decided: MIT.** Maximizes adoption ("for the masses"), and is compatible with Crawlee (Apache-2.0) and Playwright (Apache-2.0) as dependencies. Copyleft options (GPL, and especially AGPL) were rejected deliberately: AGPL in particular would bind HT's own future use, since it triggers on running a modified version as a network service — exactly what §2f's MCP/API serving layer is. Apache-2.0 was also considered (its explicit patent grant matters more for projects with heavier original patent-eligible contributions); MIT is the simpler, more universally recognized choice given Spoor's genuinely novel pieces are integration/porting work, not something that needs that extra protection. Avoid depending on anything AGPL/commercial-only; specifically, use Healenium's OSS core algorithm/approach rather than Healenium Pro (commercial, adds SaaS features this project doesn't need).

## 4. Phased roadmap

Scope is all four tiers for v1 per your call, but "all four tiers" doesn't have to mean "all four polished." Sequencing them so something real ships early is what keeps this from becoming a months-long black box:

**Phase 0 — Setup (few days)**
Repo scaffold, license, `pyproject.toml` (distribution name **`ht-spoor`** — the plain `spoor` name is taken on PyPI by an unrelated package; project/brand/CLI/repo name all stay **Spoor**, only the `pip install` name carries the prefix), CI (lint + test), contribution guidelines, issue templates.

**Phase 1 — Tiers 1–2, config format, and basic output (1.5–2.5 weeks)**
Wire up Crawlee's adaptive crawler almost as-is — highest-value, lowest-risk work, a thin wrapper around a mature library. Add the §2a declarative config parser and a first pass at the §2d output pipeline (JSON/CSV) and politeness policy in the same phase, since without these the tool has no real user-facing surface yet. Ship this alone as an early v0.1 if you want real feedback fast.

**Phase 2 — Tier 4, human interaction (3–5 days)**
Playwright's primitives plus the jitter/easing wrapper. No ML, no fragile heuristics — quick to build and test, and it's useful on its own (e.g. defeating simple bot checks) even before tier 3 exists.

**Phase 2.5 — API surface discovery + default signal capture (1–2 weeks, can run in parallel with Phase 2/3)**
Spec discovery + GraphQL introspection probes (days), wire in HAR recording on every Playwright context (near-free once Phase 1 exists), then the mitmproxy2swagger spike and, if it pans out, the action-correlation log. Bundle in the free/near-free signals from §2c (storage state, console/errors, accessibility tree, response headers) as default capture at the same time, since they piggyback on the same context. This only depends on Phase 1 existing, not on tiers 3–4, so it can be built alongside them rather than after.

**Phase 2.6 — Opt-in deep signals (3–5 days, only if/when needed)**
Video recording, heap snapshots, and media-manifest capture as explicit flags, not defaults — build these on demand rather than up front, since they're the least likely to be used on every run.

**Phase 3 — Tier 3, local self-healing (2–3 weeks, do not compress this phase — see §1)**
The most genuinely novel engineering here, and per §1 the single highest-priority phase in the whole plan: fingerprint capture on first success, scored matching on failure, a tunable confidence threshold, built alongside the §5.3 mutation-testing harness from the start rather than bolted on after. Expect this phase to need the most iteration and real-world testing against sites that change their markup — that's expected, not a sign something's wrong.

**Phase 3.5 — Reliability essentials (1–1.5 weeks)**
The rest of §2d. **Delivered:** retry/error classification with a dead-letter log (the tier-1 fetch path — see the Phase-3.5 decision note in §2d), browser-tier navigation retry (the same classification/backoff wrapping `page.goto`, so a transient navigation failure no longer crashes the run — see its decision note), anti-bot/CAPTCHA detection (fail loudly, detection-not-bypass — including challenges served *behind* an error status, carried on the `FetchFailure` and surfaced beside the dead-letter line — see its decision note), change detection (ETag/`Last-Modified`/content-hash skip of unchanged pages, opt-in — see its decision note), and the run-summary observability output (Phase 1, now also carrying the dead-letter log, retry count, challenge, and unchanged-page count). This completes §2d's reliability essentials. Sat naturally after Phase 3 since it's the same "handle things going wrong gracefully" mindset as self-healing, just at the request/run level instead of the element level.

**Phase 4 — "For the masses" packaging + v1 surface (1–2 weeks)**
PyPI publish as **`ht-spoor`** (`pip install ht-spoor`, imports/CLI still `spoor`), CLI polish, docs site fronted by the hero sentence, 3–5 worked example configs (§2a) against public scraping-practice sites, a short "why not just use Crawl4AI" positioning note in the README, GitHub Discussions or Discord for community, and a first-pass §2f MCP/API server exposing whatever §2a/§2b have already captured (the fuller version, serving the §2e exploration graph, follows once v2 ships). Two extension points are **documented, not built — just the interface**: the proxy hook, and the optional AI fallback (`resolver.set_ai_fallback(fn)`, tier 3.5) so a power user can wire in Claude/GPT/a local Ollama VLM with no default provider shipped and the core staying dependency-free. (This absorbs what an earlier draft split out as a standalone "Phase 4 — AI fallback"; see the decision note below.)

Realistic total: **9–13 weeks** of focused work for a genuinely usable v1 (four UI tiers, API surface discovery, the declarative config interface, and the operational essentials that make it a real tool rather than a library fragment). Phase 3 (tier-3 healing accuracy) is still the likeliest to run long; Phase 3.5 is the next-most-likely, since "graceful failure" only gets exercised properly against real, messy, occasionally-hostile sites.

**Decision — the optional AI fallback is folded into packaging, not a standalone phase.** An earlier draft sequenced the tier-3.5 AI fallback as its own "Phase 4" ahead of packaging. It is deliberately the smallest, lowest-stakes item in the plan — off by default, no provider shipped, a thin `set_ai_fallback(fn)` seam whose whole purpose is to keep AI *out* of the dependency-free core (§1). Given that, standing it up as its own phase over-weighted it: AI is explicitly not the product's differentiator. It is therefore folded into the packaging phase as a **documented extension point built to the same "interface only, not implemented" bar as the proxy hook** — the seam exists and is documented at v1 launch, but no phase is spent building a provider around it. A concrete provider integration lands only if a real user need pulls it in. This changes *sequencing only*: the tier-3.5 capability itself (§2 tier table, §7 dependency table) is unchanged.

**Phase 5 — Exploration mode + wiki generation (v2, ~6–9 weeks, starts after v1 ships)**
The full §2e system: state-abstraction tuning, the sandbox-only destructive-action safety system (with its own dedicated test suite proving it can't be bypassed against a non-sandbox target), graph storage, and wiki templating. Deliberately sequenced after v1 rather than folded into it — it depends on the tiers, signals, and action-correlation groundwork from Phases 1–3.5 already existing and being stable, and it's substantial enough on its own that bundling it into the v1 estimate would just make that number meaningless.

## 4a. Repository setup & development approach

**Feature development is BDD-first, layered on top of the existing test pyramid (§5), not a replacement for it.** Every named capability in this plan (§2a extraction, §2d operational essentials, §2e exploration safety, §2f MCP/API serving, §2h data handling) gets a `.feature` file written in Gherkin (Given/When/Then), using `pytest-bdd` so it plugs directly into the same `pytest`/`hypothesis`/`pytest-cov` stack already committed to in §7, rather than adding a second test runner. ## 5. Testing strategy & test bench design

**Honest framing first, since reliability is now the top priority (§1): "100% accuracy" isn't a real target for a system that must generalize to arbitrary, unknown websites — no adaptive, heuristic-driven mechanism can be proven correct against input it's never seen.** What's achievable, and what this section actually designs for, is a *measured, tracked* accuracy standard: a known success rate against a large, growing corpus of realistic mutations, regressions caught automatically before they reach a user, and an honest published number rather than a marketing claim. §6 already says not to oversell tier 4's stealth in marketing copy — the same discipline applies here to tier 3's reliability.

### 5.1 The fixture layer

- **Static local fixture pages** (checked into the repo) for deterministic per-tier unit tests — hand-built HTML/JS pages that isolate one mechanism each (one page whose element class name changes every reload, to drive tier-3 healing tests deterministically; one that requires JS to render a field, to test tier-2 escalation; one with WebSocket traffic, to test §2c capture) — these exist because the archetype apps below are realistic but not fully controllable, and deterministic unit tests need fully controllable inputs.
- **Public scraping-practice sandboxes** (`books.toscrape.com`, `quotes.toscrape.com`) for basic integration tests and demos — legal, stable, and exactly what "the masses" will try the tool against first.
- **The archetype matrix, purely as validation fixtures (see §0 — never as integrations the core code knows about):** OWASP Juice Shop (security-flavored webshop + API, self-hosted via Docker), Sauce Demo (clean login-gated webshop: login/cart/checkout, self-hosted via Docker — never the live `saucedemo.com`, per the out-of-scope note below), a self-hosted ERPNext or Odoo instance (auth-gated internal app: heavy tables, forms, workflows), and a self-hosted open-source Netflix-clone (heavy client-rendered SPA + media state). If one archetype needs a special case to pass, that's a bug in the general mechanism, not a fixture to special-case around.
- **A `docker-compose.yml` test bench** bringing up all four fixtures at once, each declared `sandbox: true` (so §2e's exploration mode can exercise destructive actions safely against them) — what CI and local exploration-mode testing runs against.
- A small **nightly job** against a handful of real-world sites (permissive robots.txt) to catch drift before users hit it.

**Explicitly out of scope as a test target:** a real company's live production site (e.g. Netflix's actual service) — it teaches the suite nothing the self-hosted clone doesn't already cover, and ties CI health to a target nobody controls.

**Decision — Phase-1 in-vivo bench (Juice Shop only).** The `docker-compose.yml` bench (`fixtures/docker-compose.yml`) is introduced in Phase 1 with **only OWASP Juice Shop** stood up, not the full four-app matrix. Juice Shop is an Angular SPA whose product listing renders client-side, so it exercises exactly what Phase 1 built end-to-end against a real, uncontrolled app: tier 1 finds nothing, the dispatcher escalates, tier 2 renders in a browser and extracts. The other three archetypes gate on capabilities that do not exist yet — Sauce Demo and ERPNext/Odoo need auth (Phase 2+), Juice Shop's API surface needs §2b discovery (Phase 2.5), and destructive-action exploration needs §2e (Phase 5) — so standing them up now would be scaffolding, not validation; they join the same bench as their phases arrive. Per §5.2 the docker E2E smoke is a **pre-merge gate**, so CI boots the container and runs it on every PR; locally the integration test **skips gracefully** when the container isn't reachable, keeping the fast unit gate network- and Docker-free. Juice Shop is pinned to a specific image tag for determinism. The `sandbox: true` declaration §5.1 calls for is recorded as a compose label until the §2e registry consumes it. Because the pinned image is deterministic, the run's extracted records are both written to a durable path and uploaded as a CI artifact **and** diffed against a committed golden master (`tests/golden/`) — the first concrete seed of §5.4 dogfooding, so a silent change in Spoor *or* the fixture is surfaced. CI caches the pip download, the Playwright browser, and the pinned image tarball to keep the gate fast (~30s) as heavier archetypes join the bench later.

**Decision — Sauce Demo joins the bench (second archetype, first login-gated).** With bring-your-own-session (§2h) shipped, the capability that can actually exercise a login-gated app now exists, so Sauce Demo joins the bench. It earns its place on two counts: it is a structurally different SPA from Juice Shop (a second §0 no-tailoring data point — the same unmodified tiers resolve both), and its inventory is reachable only behind a login, making it the first *end-to-end* proof of BYO-session against a real app rather than the synthetic loopback server `session.feature` uses. No official or trustworthy prebuilt image exists, so it is built from a **pinned source commit** of `saucelabs/sample-app-web` (a static React/Vite build served by nginx; `fixtures/sauce-demo/`) — pinned for the same determinism reason Juice Shop pins an image tag. The bench host port defaults to 3001 and is overridable (`SAUCE_DEMO_PORT`) for machines where 3001 is taken; the integration test reads the matching base from `SPOOR_SAUCE_DEMO_BASE`. Two integration tests (`tests/test_integration_sauce_demo.py`) capture the guarantee: a browser-tier run **without** a session is redirected to the login page and extracts nothing (the gate is real), and a run **with** a session the test captured the way a user would (Spoor never logs in — that would be a per-site flow violating §0) escalates from the empty static shell to the browser tier and extracts the gated inventory, diffed against a committed golden master (§5.4). The `session-username` login cookie is short-lived, so the session is captured fresh per run rather than committed (which also keeps a secret out of the repo).

**Decision — PrestaShop joins the bench (third archetype, first server-rendered storefront).** The two existing archetypes are both SPAs whose whole app effectively lives at one URL — which under-exercises exactly the part of §2e the 7-series has been hardening: mapping a *large, deeply-linked, stateful, multi-page* site with real navigation, forms, and per-page URLs. PrestaShop fills that gap: a mainstream PHP/MySQL e-commerce platform whose catalog, category pages, product pages, cart, and checkout are ordinary server-rendered pages — the structural opposite of Juice Shop and Sauce Demo, and a much richer graph for reset-and-replay, state abstraction, and coverage measurement to chew on. It is stood up from the **official `prestashop/prestashop:8.1` image**, pinned by tag for the same determinism reason the other two pin (Juice Shop's image tag, Sauce Demo's source commit). Unlike the distroless SPAs it needs a datastore, so it ships as **two services** — `prestashop` plus a `mariadb:11` `prestashop-db` (infrastructure, *not* itself a scrape target, so no `sandbox` label and no host port) — and **auto-installs on first boot** (`PS_INSTALL_AUTO=1`): the first `up` takes a few minutes to build the schema and demo catalog, then persists in a Docker volume so later boots are fast. `PS_DOMAIN` is pinned to the published `127.0.0.1:<port>` so generated links resolve to the served host. The bench host port defaults to **8080** (PrestaShop's conventional dev port; the 300x range is taken) and is overridable via `PRESTASHOP_PORT`. Like the others it carries the `spoor.sandbox: "true"` label so §2e exploration may exercise it freely. *Deliberately not shipped in this change:* an integration test and golden master — a full storefront's exact graph is a poor golden (its demo catalog and session state vary), so a PrestaShop integration test wants a structural-completeness contract like `tests/test_integration_wiki.py`'s rather than a record diff, and that is its own BDD-first slice. This change stands the target up and documents it; wiring it into the automated bench (the CI boot matrix and an exploration reliability test against it) follows.

**Decision — the bench also validates the §2f serving round-trip end-to-end.** The read-only serving layer (§2f REST + MCP, with the §2h redaction and API-surface projection) was built and tested in isolation against a synthetic in-memory `MapStore`; it had no proof it holds against a *real* capture. `tests/test_integration_serving.py` closes that: it runs the dispatcher against live Juice Shop, records the result the exact way the `spoor run` command does (`shareable_api_surface` → `MapStore.record`), reads it back through a **fresh** store (so the on-disk JSON round-trip is real, not an in-memory shortcut), and serves it over **both** surfaces — the REST API via Starlette's `TestClient` and the MCP server in-process. It asserts each surface returns the same records the run produced (post-redaction, §2h), carries a non-negative freshness age (§2f), agrees with the other, and refuses an unmapped URL rather than fabricating one; the MCP surface's read-only/non-destructive tool annotations (the §2f non-negotiable) are asserted against a real capture, not just a fixture. This reuses the same skip-when-Docker-down pattern as the other archetype tests, so the fast unit gate stays Docker-free. No serving code changed — the layer already held; this is the missing archetype-bench proof that it does.

**Decision — test tiering: a seconds-fast local gate, the full suite on CI.** The suite had grown to the point where a plain local `pytest` took ~10 minutes, because the browser-launching scenarios (real headless Chromium) and the docker-archetype integration tests ran alongside the in-process unit and fake-driver BDD tests. That is the wrong default for the edit-run loop: local should be fast, CI can be thorough. The split is by pytest marker. Two slow tiers are tagged — `browser` (anything that launches a real Chromium; applied per *scenario* via Gherkin `@browser` tags on the browser-tier scenarios, not per file, because most step files are mixed: a browser scenario beside network-free `mock_client`/tier-1 scenarios) and the existing `integration` (needs a live docker archetype). `pyproject.toml`'s `addopts` deselects both by default (`-m 'not browser and not integration'`), so a bare local `pytest` runs only the in-process tier in seconds; CI overrides it with `pytest -m ""` (empty expression = run everything) so the browser tier and, with the container up, the Juice Shop end-to-end still gate every PR. On demand, a developer runs `pytest -m browser`, `pytest -m integration`, or `pytest -m ""` locally. One test-isolation defect surfaced doing this: the `test_escalation.py` walk tests called `run_report()` with no client, so the §2b companion API probe opened a real `httpx.Client` and hit `http://localhost/x` — a multi-second timeout per test; they now take the `mock_client` fixture purely to keep that probe off the network.

**Decision — Sauce Demo dropped from the *exploration* bench, kept for extraction/session.** The live-archetype wiki-reliability test (`tests/test_integration_wiki.py`) previously crawled both Juice Shop and Sauce Demo; the Sauce Demo parametrization is removed. Sauce Demo's whole app sits behind a login wall, so an *unauthenticated* exploration crawl (which is what that test runs — it does not inject a session) reaches only the login page and maps nothing worth asserting a completeness contract over. Sauce Demo keeps its place in the bench where it earns it: `tests/test_integration_sauce_demo.py` (the bring-your-own-session §2h end-to-end and the §0 second-data-point extraction proof), its container, configs, and golden master are all retained. This narrows one test's scope; it does not retire the archetype.

**Backlog (next design fork) — richer CI: more archetypes booted, and performance testing on CI.** With containers already booting on CI (Juice Shop today) and the fast-local/full-CI split in place, CI has headroom to do more than local ever should: boot the heavier archetypes (Sauce Demo, PrestaShop, and the ERP/Netflix-clone as their phases arrive) as a matrix, and run the §5.2 load/concurrency (`locust`) and chaos/fault-injection (`toxiproxy`) tiers that only make sense against live services and are far too slow for a local gate. This is recorded as the next test-infra design fork, not built here — it wants its own decision on runner cost, matrix shape, and which tiers gate a merge versus report advisory numbers.

### 5.2 Test types, mapped to what each actually validates

| Test type | Tool | What it catches |
|---|---|---|
| Unit tests | `pytest` | Each tier's logic in isolation against static fixtures — fast, deterministic, run on every commit. |
| Property-based / mutation testing (tier 3 specifically) | `hypothesis` (MIT) | See §5.3 — this is the one that actually matters most given §1's reliability priority. |
| Golden-master regression | `pytest` + Spoor's own captured output | See §5.4 — using Spoor's own maps as the "did anything silently change" baseline, including §2g's generated assertions. |
| Chaos / fault injection | `toxiproxy` (Apache-2.0) | Network latency, dropped connections, slow responses, injected between Spoor and the fixtures — proves §2d's retry/backoff/error-classification actually handles real-world messiness instead of just the happy path. |
| Load / concurrency | `locust` (MIT) | Confirms the §2d politeness policy actually caps concurrency and backs off under load, not just in a single-request test. |
| Safety / sandbox-bypass (adversarial) | `pytest` | Deliberately tries to trick the §2e destructive-action guard (malformed sandbox declarations, edge-case URLs) and asserts it never fires against a non-sandbox target. Given the weight put on that guarantee, this needs its own dedicated suite, not incidental coverage. |
| MCP/API contract tests | `pytest` + schema validation | §2f's responses match their declared schema, and the freshness/staleness signal (§2f) is actually present and accurate on every response. |
| Genericity enforcement (§0) | A small custom script, in CI | Scans core source for hardcoded hostnames/domain strings outside the recognizers/fixtures config, fails the build if found — turns §0's "no site-tailoring" design principle into an automated, unbypassable check rather than a code-review hope. |
| End-to-end smoke | CLI run against each fixture | Cheap, fast pre-merge gate: did the whole pipeline actually run and produce non-empty, valid output. |
| Coverage tracking | `pytest-cov` | Baseline metric, tracked over time — not a target to game, but a signal if a whole code path has zero test contact. |

### 5.3 Tier 3 gets the most rigorous testing in the plan, on purpose

Given §1: this is the piece that can't be flaky. The design: a **mutation harness** takes a known-good fixture (one where tier 1/2 correctly finds an element) and applies a battery of realistic DOM mutations — class renames, attribute shuffles, element reordering, added wrapper elements, text changes, combinations of the above at increasing severity — then asserts tier 3 still resolves to the *correct* element above a defined confidence threshold. Using `hypothesis` to generate mutation variants (rather than hand-writing a fixed list) means the corpus grows and explores far more of the space automatically than example-based tests alone. The tracked output is a **success rate against this corpus**, published and monitored for regression on every change to tier 3 — that number, not a one-time claim, is what "reliable" actually means here.

**Concrete v1 target (decided): ≥95% correct-element resolution on the mutation corpus**, tracked per release and gating a Phase 3 "done" call — not just an open-ended measured number with no bar to clear. Anything below that threshold on a given mutation class is a known gap to fix before shipping, not a footnote.

### 5.4 Dogfooding: Spoor's own captured maps as regression tests

Once Spoor maps a fixture's behavior (via §2a or §2e), that map is a golden master: state X, action Y, signal bundle Z. Re-running Spoor against the same fixture later should reproduce a matching bundle — a diff-based test asserts nothing silently changed, in either the fixture *or* Spoor's own behavior, and this doubles as a concrete demonstration of exactly what §2g (generated test automation) produces for an end user. This is testing the tool with the tool, run on every CI pass against the docker-compose fixtures in §5.1.

**On exact reproducibility:** Spoor does not promise byte-identical output run-to-run against a real, live target — the target itself can change, tier 3 can legitimately heal to a different-but-equally-correct element, and async network timing varies. The golden-master/diff approach above *is* the reproducibility model: not "identical every time," but "any change gets surfaced and reviewed," which is the honest version of reproducibility a system like this can actually deliver.

### 5.5 Performance bench & trend dashboard (decided; small set shipped)

A continuous performance bench runs the real exploration pipeline against the pinned §5.1 archetypes in CI and trends the numbers over time, so a performance regression (or a coverage regression) is caught as drift rather than discovered by a user. Three sets, sized for how often they can afford to run:

- **Small** — a tight, count-bounded Juice Shop crawl. Cheap enough to run **in parallel with the CI gate** on every push/PR (its own job and container, so it never gates or is gated by the suite).
- **Mid** — a larger-budget Juice Shop crawl. Nightly.
- **Large** — a PrestaShop crawl (server-rendered, deeply linked, DB-backed; needs the image/volume cached like CI caches the Juice Shop tarball). Nightly or weekly.

**The metrics split in two, and this split is the whole design.** For a *pinned* target and a **count-based** budget (`max_states`/`max_depth` — never `max_seconds`, whose stop point would depend on runner speed), the *map* the crawl builds is deterministic (§0), so the **graph-shape counters** reproduce exactly run to run and are **gated** against a committed baseline (fail the run on any drift, the golden-master model of §5.4 applied to the crawl shape): states, transitions (actuated actions), skips, and the total actions *discovered* (coverage — read against actuated/skipped it shows how much of what was found was driven). These held identical across every CI run.

What is *not* reproducible — and seeding the baseline proved this empirically, which is exactly why §5.5 requires a CI-seeded baseline to be inspected before the gate is trusted — is anything downstream of the **walk**: the **per-operation call counts** (`reset`/`state_html`/`ax_nodes`/`probe`/`perform` …), the **skip-reason message**, *and even the capture counts* (`image_files`/`image_refs`). The walk's replay/recovery loop reacts to the live target's runtime nondeterminism (Juice Shop is an SPA whose reset does not always land in the same place), so the number of replay retries — and occasionally an extra element capture — differs run to run even when the map is identical: a check run caught `image_refs` moving 151→152 with states/transitions/skips/discovered unchanged. So all of these are **reported as advisory only, never gated** (dedup stays observable as files-vs-refs; the counts feed triage). This corrects the earlier assumption that the per-operation call counts and the dedup counts were deterministic — only the graph shape is. Dedup *correctness* is still protected, by slice 8g's own unit and browser tests, not by this gate.

Wall-clock timing, by contrast, swings on GitHub's shared runners, so it is an **advisory trend only** (charted via `benchmark-action/github-action-benchmark` on a `gh-pages` branch, alert-on-regression comment, never a hard failure). Timing is taken **per browser operation, not as one whole-run blob**: each driver call is one "transaction", and the bench reports each operation's median, p95 and total across the run. This is deliberate and is what makes the timing usable — a regression *localises* ("`screenshot` got 2× slower", not "the run got slower"), and each operation yields many samples per run, so its **median** is far more stable against a noisy neighbour than a single end-to-end total. Two further **localisation aids** (advisory, never gating) turn "the run is slow" into "slow *here, because of this*": a **triage verdict** that reads the deterministic result against the timing (counters unchanged ⇒ a slowdown is perf-code or runner noise; counters changed ⇒ the run did different work that likely explains it), and the **slowest individual transactions** — the specific calls, with the action each touched, that consumed the most wall-clock. This keeps runner noise out of the gate while still pointing at a real slowdown's cause.

Beyond aggregate timing, the bench collects an **event-anchored resource trace** so a regression can be located not just by *which* operation but *where in the run* it happened. Every transaction records an absolute start offset (seconds from run start) and **resident memory sampled immediately before and after the call** — bracketing each browser round-trip — using `psutil` to sum the Python process and its children so Chromium's memory is counted, not just Spoor's. Sampling on event boundaries rather than a fixed clock is deliberate: each point already knows the operation and action it belongs to, so a memory step attributes directly to the call that caused it (a fixed-cadence sampler is blind to *what* it sampled and would have to be correlated back against the transaction log anyway). The trade-off is honest — a transient that rises and falls entirely *inside* one call is invisible to boundary sampling; if that ever proves to matter, a background sampler can be layered on the same absolute-time axis later. Like the walk-dependent counters, the trace is nondeterministic run to run and is therefore a **within-run diagnostic, never gated**: it is emitted as a per-run JSON artifact (ordered `t_start`/`duration`/`op`/`detail`/`rss_before`/`rss_after` rows, ready to stretch onto a timeline), and its one scalar reduction — **peak resident memory** — rides the advisory dashboard as a smaller-is-better trend line, so a memory regression across commits surfaces alongside the timing lines. `psutil` is a dev/bench-only dependency; when it is absent the RSS readings are zero and the trace degrades to timing-only. The trace is also **rendered to an interactive HTML report** — a self-contained, dependency-free canvas chart (`scripts/assets/perftrace_report.html`, filled by `perfbench.resource_report_html`) of memory over the run's real-time axis, with each point coloured by operation, before/after series toggles, drag-to-zoom, and a per-point hover tooltip (op, action, timing, RSS before→after). The report is uploaded as a per-run artifact and, on `main`, published to `gh-pages` under `dev/trace/` (latest-only, overwritten each run; historical copies live in the artifacts) alongside the `dev/bench/` scalar dashboard. An interactive page was chosen over a static PNG so a reviewer can zoom into the moment of a spike and read the exact call that caused it.

The harness (`scripts/perfbench.py`) is generic: it takes the target URL as an argument — no archetype is hardcoded (§0), the URL lives only in the workflow — and drives the same `explore` path as the rest of the suite; its `measure`/`benchmark_entries`/`check_drift` maths is pure and unit-tested with a hand-built graph, so the fast tier covers it without a browser. **Shipped so far: the harness and the small-set job** (`.github/workflows/perf.yml`), including the event-anchored resource trace, the peak-RSS trend line, and the interactive HTML trace report published to `gh-pages`. The committed baseline is seeded once via a `workflow_dispatch --update-baseline` run and inspected before the drift gate is relied on; until a baseline is committed the small-set job records and charts but does not block. The mid and large sets land next on the nightly schedule (superseding the placeholder `nightly.yml` drift stub).

## 6. Risks worth naming up front

- **Legal/ethical, and where responsibility actually sits**: default to respecting `robots.txt` and rate-limiting; make overriding it an explicit, documented opt-out, not the default. But say this plainly and prominently in the README, not buried here — **Spoor is a technical capability, not a legal opinion or a grant of permission.** Whether it's lawful or permitted to scrape or reverse-engineer a given target's API is a question only the person pointing Spoor at it can answer, for their own situation (the target's ToS, their jurisdiction, the target's own terms). The user, not Spoor, is legally responsible for how it's pointed and used.
- **Anti-bot arms race**: tier 4's "human-like" behavior raises the bar but won't defeat serious bot detection (e.g. Cloudflare's harder tiers) — don't oversell this in marketing copy.
- **Tier 3 accuracy**: self-healing locators are the hardest part to get right; budget real iteration time here, not just initial implementation time.
- **Maintenance load**: "for the masses" means issues and PRs from people scraping sites you've never seen — decide early how much support bandwidth you actually have, and say so in the README (e.g. "best-effort" vs. actively maintained).
- **API discovery is legally touchier than UI scraping**: reverse-engineering undocumented endpoints and calling them directly bypasses whatever rate-limiting/abuse controls the official UI enforces, and many ToS treat that distinction explicitly. Worth a clear README statement that captured/synthesized specs are for understanding a product's surface, not a license to hit endpoints outside normal usage patterns.

- **Localization of keyword/heuristic resource lists** (§2e, before Phase 5) — *noted, needs sparring; not yet designed.* The §2e destructive-action guard matches an **English** keyword list (`delete`, `remove`, `buy`, `pay`, `submit`, …), and the same will be true of any name/label keyword matching the input-data mapping below relies on. On a non-English target, a destructive action whose visible label isn't in the English list would not be flagged destructive — so against a real (non-sandbox) site it would be *interacted with* rather than skipped. That makes localizing these lists a §2e **safety** concern, not cosmetics: they should become locale-aware resource files (per-language keyword sets, declared or auto-detected), with the guard **erring safe** — treat an uncovered/unknown locale as "assume destructive / skip", never "assume safe". Open to spar: how locale is declared vs. detected, where the resource files live, and the exact safe-default when a target's language isn't covered. Only bites once §2e leaves read-only mode, so it blocks Phase 5, nothing sooner.

- **Input-data provisioning for interactive modes** (§2e/§2g) — *noted, needs sparring; not yet designed.* Everything through Phase 2.5 is read-only, so Spoor never types into a field; but once it leaves read mode and starts filling inputs, adding to carts, and driving forms (§2e), it needs data to supply. Sketch to spar, not a decision: a pluggable generator seam — **Faker** (broad, likely the default), **Mimesis** (faster, optional backend), **exrex** (for regex-constrained fields, e.g. an HTML `pattern=`) — feeding a **generic** field→generator mapping driven by observable field semantics (input `type`, `pattern`/`min`/`max`/`maxlength`, `<select>` options, `required`, and name/label/ARIA keywords). Not a problem today (read-only), so nothing to build now — this is a marker that the direction is chosen and needs more sparring before it's scoped. The **first-run-generates-a-config-scaffold** shape of this seam, and the **subtractive-permission model** that keeps a second interactive round inside the §2e sandbox boundary, are now written up as the "second-round interactive exploration" design note in §2e — this §9 item stays the home for the input-data-*generation* sparring specifically.

- **Visual capture: screen/state identity + screenshots as surfaced evidence** (§2c/§2e/§2g/§2h) — *in progress (§2e slice 8): the screenshots-in-the-wiki strand of this item is now designed and being built as the staged, opt-in slice 8 (see the slice-8 decomposition note above); 8a shipped the pure-renderer embedding and 8b shipped the live capture, the `render_wiki` image writer, and the `spoor explore --screenshots` opt-in flag, so stage 1 (a full-page screenshot per state, embedded on opt-in) is complete; 8c grouped the images into a `screenshots/` subfolder, 8d added stage-3 per-element clips filling 6e's Screen-capture column, and 8e added the opened-contents capture (open a gate-permitted disclosure element, screenshot what it reveals, Escape-restore) in a new "Opened contents" column — completing the maintainer's "the dropdown and its contents in a separate column" request. The screen/state-identity strand (folding the visual hash into how states are told apart) remains as below.* Two related needs surfaced that the plan doesn't yet cover: (1) telling **visually-distinct screens apart** even when their text/DOM is equivalent — e.g. a "Main screen" that is the *maintenance* home vs. the *order* home — which today's state identity cannot do, because state identity is defined as normalize-the-DOM-and-hash (§2e prior-art note) with **no visual component**, so two such screens collapse to one state; and (2) **seeing the acting element** ("show me the button that gets pressed") and the resulting screen as visual evidence in the §2e wiki and the §2g test record — today the action/transition record carries a page-level state screenshot at most, never the element's own cropped image. Direction to spar, staged so early value doesn't wait on the v2 wiki (§2e, Phase 5): **(a)** make a screenshot a *kept* local-only artifact (like the HAR/storage captures, §2h) and compute its **perceptual hash** (the `spoor/core/visual.py` dHash already exists, used element-level for tier-3 healing) — the hash is a 64-bit integer, so *surfacing it* on the run summary/map is §2h-clean and already answers "maintenance vs. order screen" without any pixels leaving local; **(b)** fold that visual hash into how screens/states are told apart, and attach the element screenshot as a **reference** (local path + hash + dimensions, all text) to the shipped §2b action↔request correlation record; **(c)** deliver actual **pixels** only as a **curated, explicit export** — the wiki generates locally with images referenced by relative path, and a selected image pack (e.g. a zip alongside the static site) leaves the machine only on a deliberate user action. Hard constraints so the eventual design doesn't drift: hashing/screenshotting is generic and stays in `core/`/`visual.py` (§0, already true); binary **cannot** be pattern-redacted, so §2h's text redaction does not make a screenshot safe — pixels reach a shared surface only via the **explicit-opt-in export** §2h already sanctions for the raw cache, with human curation standing in for redaction; and the visual hash from (a) is what makes that curation tractable (dedup near-identical screens, export only the distinct ones). Not building now; recorded so the direction and its §2h boundary aren't lost.
